# 故障案例与恢复

> 本文件是 babeldoc-trans 的**故障案例库**：记录实际遇到过的异常现象、根因与恢复流程。
> 遇到「想不通为什么」的异常（如 `pending` 为空、覆盖率假 1.0、无法重跑、渲染命中率低等），先在这里翻相似案例。
> 新增案例请复制文末「模板」段落到上方、顺延编号即可。

## 文件角色速查（所有案例共用）

- **`source_texts.jsonl`（权威源）**：阶段 1 `--collect-only` 产出，含全部待译段，每行 `{"input": <原文>, ...}`。不重跑 collect 就固定不变，是**唯一可信的真值**。
- **`pending.jsonl`（派生清单）**：由 `source_texts` 减「已有译文」算出的差集，带 `k = md5(input)[:12]` 短哈希键。**算出来的、不可信**，不要当真值。
- **`translations.jsonl`（译文库 / canonical）**：阶段 2 `--merge` **覆盖式**生成，格式 `[{"input": <原文逐字>, "output": <译文>}]`，**以原文为键**。阶段 3 只读这一个文件。
- **正常环**：`--collect-only` → 读 `pending` 翻译 → 写 `_batch_*.jsonl` → `--merge` 进 `translations` → `--status` 刷覆盖率 → 无 flag 渲染。

## 案例 1 — 残留坏 translations.jsonl 导致流水线自锁（catch-22）

**现象**：覆盖率报 1.0、`pending.jsonl` 被改写为 0 行，但译文实际带标签异常（如漏 `</b6>`/`</b3>` 闭合、标签顺序错），任何重跑都无法修正。

**根因（两层叠加）**：
1. `--status` 重算差集把 `pending.jsonl` 掏空（判定「没活儿了」），待办清单消失。
2. 「已译完」的判断依据是**一份坏的 `translations.jsonl`**——它使 `--collect-only` 误判「全部都在、覆盖率 1.0」而拒绝回填 `pending`；若批次重建脚本改读 `source_texts.jsonl`（只有 `input`、无 `k` 字段）会直接 `KeyError: 'k'`。

**核心规律**：`translations.jsonl` 既当「成果」又当「进度判据」，一旦残留坏版本，就用「覆盖率 1.0」伪装「已完成」从而锁死重跑；`pending` 是派生的、不可信。

**恢复（绕开 pending，从权威源重建）**：
1. 确认 `source_texts.jsonl` 是真相：条数完整、每段都有 `input`，未被污染。
2. 重建批次时**自己对每段现算 `k = md5(input)[:12]`**：不要从空 `pending` 取 `k`；依据 `source_texts` 的 `input` 逐段填入已确认的译文（无法翻译的参考文献 / 作者行原样返回）。彻底摆脱对空 `pending` 的依赖。
3. 写 canonical 批次：每行 `{"input": <原文>, "output": <译文>}`；并**显式补一条标题** `{"input": "__TITLE__", "output": "<中文标题>"}`（标题是合成键，不在 `source_texts` 里，不补会导致成品 PDF 文件名退化为英文）。
4. `--merge --status` 一次性修正：`--merge` **覆盖式**重写 `translations.jsonl`（不读旧版，坏版本直接被盖掉），同时做标签 / 占位符校验，应得 0 异常、0 未知 k；`--status` 随即报覆盖率 1.0。
5. 阶段 3 渲染：无 flag 运行，全部命中注入，产出最终中文 PDF。

> 关键：标签异常要在合并**前**于译文里先修对（补闭合标签、调顺序），`--merge` 重跑后才会真正进译文库。

**提示**：
- 中断后续跑前，先确认 `translations.jsonl` 是干净版本，不要保留「能渲染但带标签异常」的旧库。
- 任何时候都不要把 `pending.jsonl` 当真值；重建任务一律回 `source_texts.jsonl`。
- 批次重建辅助脚本读 `source_texts` 时必须自己算 `k`，不能假设输入带 `k` 字段。

## 案例 2 — Windows MAX_PATH 超长导致阶段 3 写盘失败（FileNotFoundError / FzErrorSystem code=2）

**现象**：阶段 1（collect）正常、覆盖率 100%、注入 134/134，但渲染结尾报
`FileNotFoundError: ... work\<自动目录>\<长英文文件名>.no_watermark.zh.mono.pdf`，
随后 pymupdf 兜底也失败（`FzErrorSystem: code=2: cannot open file`，路径在 traceback 里被截断显示），
脚本以 `RuntimeError: babeldoc 执行失败: code=2: cannot open file ...` 退出。

**根因**：源 PDF 所在目录本身层级深 + 文件名长（如论文全名），默认 work 目录
`<源目录>\work\<源文件名截断>_<hash>\` 再叠加 babeldoc 中间文件名
（`<源文件名>.no_watermark.zh.mono.pdf`），全路径超过 Windows MAX_PATH（260 字符）。
collect 阶段不产生这么长的中间文件名所以能过；渲染阶段才会爆。

**核心规律**：判断是否 MAX_PATH 问题——traceback 里路径显示被截断、源目录层级深、
源文件名长，三者同时出现基本可锁定；与译文内容无关，不用动 translations。

**恢复（先试方案 A，不行再用方案 B；译文均零损失）**：

**方案 A（首选，最简单）——用 `\\?\` 扩展长度路径前缀绕开 MAX_PATH**：
Windows 的扩展长度路径语法可以直接突破 260 字符限制，格式为
`\\?\` + `盘符:` + `\` + `完整路径`，例如 `\\?\D:\我的项目\一份有非常非常长名字的文件.pdf`。
给 translate.py 传路径时（源 PDF、`--work-dir`、`--output-dir`）一律改用这种带前缀的绝对路径重跑阶段 3，
**无需移动或复制任何文件**，原 work 目录直接复用。前缀要求路径为绝对路径、且分隔符用反斜杠 `\`。

**方案 B（兜底）——换短 work-dir 重跑渲染**：
1. 译文成果在 `<旧work>\translations.jsonl`（连同 `source_texts.jsonl`、`meta.json`、`auto_filled.json`）里，不受失败影响。
2. 建一个**短路径**工作目录，如 `D:\bw\<短名>`，把上述 4 个文件复制进去。
3. 重跑阶段 3 并显式指定：`python translate.py "<源PDF>" --work-dir "D:\bw\<短名>"`
   （stage_render 只从 --work-dir 读这 4 个文件，babeldoc 中间 PDF 也落在该短目录，绕过 MAX_PATH）。
4. 成品 `{中文标题}.pdf` 仍写入默认输出位置（源 PDF 同目录），中文标题文件名短，不会超限。

**提示**：
- 若环境或工具链不支持该前缀，再退而用 `--work-dir` 指到短路径（如 `D:\bw\<短名>`），避免白跑两遍版面分析。
