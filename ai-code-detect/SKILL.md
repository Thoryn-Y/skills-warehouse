# AI 代码特征检测

## 定位（先读这一段）

本技能只回答一个问题：

> **这段（项目）代码是不是 AI 生成的？哪些部分是？AI 参与面有多大？**

它**明确不回答**以下问题，也不应把它们混进来：

| 不回答的问题 | 原因 |
|---|---|
| 这段代码有没有 bug | 与“是否 AI 生成”正交。需要缺陷扫描时用 `ai-code-defect-scan` |
| 代码质量好不好、可维护性如何 | 那是质量评估，不是归因检测 |
| 代码能不能跑起来 | 在真正需要做这种检测的场景里，项目通常已经能跑了；能不能跑对归因没有信息量 |

**为什么必须切开**：一个项目可以“AI 生成且完全正确”，也可以“人工手写且到处是 bug”。把正确性拉进检测框架，会让判定被“这段逻辑看起来有问题”带偏——而 AI 写的代码恰恰读起来最像对的。检测只认痕迹，不认对错。

若检测过程中顺手看到疑似缺陷，只在报告末尾用一行注明“另见 N 处疑似缺陷，未展开”，然后把控制权交回用户，**不输出缺陷表**。

## 核心原理

**AI 生成代码的可检测性来自它的“均匀”。**

人的代码在同一项目内是参差的：有的函数注释密集，有的干脆没有；有的地方防御到啰嗦，有的地方一行不写；命名长度随手而变；错误处理密度忽高忽低。因为这些代码写于不同时间、不同心情、不同紧迫度。

AI 的输出则像一位全程保持同等专注度的作者：**注释密度恒定、防御代码均匀、命名对称、结构齐整、不做取舍**。

**但“均匀”只是痕迹的一半，而且是最容易褪色的那一半。**

它只在“单次、无上下文、模板驱动”的生成下成立。多轮逐模块生成时，每个文件按当次任务定量，参差会自然出现；读过项目文档、或被要求“按现有风格、少写注释”时，“满配”也不会出现。

**换一层看，痕迹仍在，而且更耐改写：迭代不会让代码变得像人写的，它只会压平文体，压不平纪律。** 人连续数周做同一个项目，纪律必然漂移——赶工那天少写文档，重构那天多写注释，新学的写法只用在新文件里，被废弃的函数删了但 import 忘删。agent 每轮开工都重读同一份约定，然后把同一套规范**原样重放**，它没有“那天太累了”。

于是痕迹从“多出来的东西”翻转为“**本该有的东西没有**”：

- 调试时注释掉一行、留个 TODO、删函数忘删 import —— 一处都没有；
- 本该随函数重要性衰减的文档密度 —— 不衰减，私有方法与公共方法一视同仁。

所以检测有两条入口，都要走：

| 轴 | 测什么 | 认哪类生成 | 详见 |
|---|---|---|---|
| **A 表层** | 过度均匀、与仓库基线失配 | 速成代码：单次、无上下文、模板驱动 | 本文件评分量表 |
| **B 纪律** | 文档风格与注释组织**同时**偏离人工惯例 | 迭代式生成：多轮 agent + 人类把关 | `references/iterative-generation.md` |

**轴 A 归零不等于没有痕迹。** 只留轴 A 的检测，会把一整类多轮生成的代码判成 0 分——这个错误曾经写进本技能的“检不出”边界，现已推翻（见 `references/detection-limits.md` 第八节）。**轴 A 为 0 时必须继续跑轴 B。**

除此之外最有效的两个动作不变：

1. **建立基线**（该仓库人类代码、或对照语料的统计分布），再找离群。
2. **看元证据**（占位符残留、AI 自述与自署名、工具痕迹），它比读代码可靠得多。

## 四层痕迹模型

| 层 | 看什么 | 为什么有效 | 可靠性 |
|---|---|---|---|
| **T1 文体指纹** | 注释、命名、防御、语法糖、排版节奏 | 生成器的默认习惯高度稳定 | 中。须与项目基线对比，否则会冤枉严格规范的人类代码 |
| **T2 结构指纹** | 文件体量分布、模块对称性、复用关系、依赖引入 | 单次生成的产物缺演进痕迹 | 中高。项目级比文件级可靠 |
| **T3 元证据** | 占位符残留、AI 自述与自署名、工具与配置文件痕迹 | 与生成过程直接相关，不受风格伪装影响 | **分化，不齐平**：S1 类一条即可改判定；工具配置类只证明“用过 AI”，不证明“这段是它写的”，仅作加分项 |
| **T4 纪律痕迹** | 文档风格是否偏离（docstring 全覆盖、注释稀疏、私有方法同等待遇）、注释组织是否偏离（分区注释密度）、残留物是否缺失 | 迭代压平文体，但压不平纪律；人必然漂移，agent 不会 | **中高，但必须校准，且须两条同时成立**。单条判据只反映项目风格；绝对分无意义，须除以人工基线得出倍数，≥10× 才可作强证据 |

**优先级：T3 > T4 ≥ T2 > T1。** T1 单独不足以判到“高度疑似”（强信号全为 T1 时最高只能到“混合”，见判定区间）；T3 里只有生成器残留与自述（S1）能单独定案，工具配置痕迹做不到；T4 的强度取决于基线倍数，没跑基线就退回 T2 的份量。

全量条目、AI 典型 vs 人类典型的对照、逐条检测命令见 `references/traits-catalog.md`。T4 的完整方法论见 `references/iterative-generation.md`。

## 评分量表

每条痕迹按辨识力给权重，累加后落区间。**这是启发式排序，不是概率**——不要说成“87% 可能是 AI”。

### 强信号（各 12 分，共 60）

| 编号 | 痕迹 | 判据 |
|---|---|---|
| S1 | **生成器残留物** | `# Your code here`、`<!-- 在此处填写 -->`、`[insert ...]`、生成器自述（`As an AI`、`作为一个 AI 语言模型`）、`Generated by <model>` 类自署名；以及“文件已标完成、函数体却只有 `pass` 或 `NotImplementedError`” |
| S2 | **与仓库基线全面失配** | 命名约定、注释语言、错误处理、import 组织、缩进风格中 ≥4 项同时不同于同目录既有文件 |
| S3 | **装饰性符号** | emoji、box-drawing（`╔═╗`）、`# ===== 分区 =====`，且**仅出现在新文件**里 |
| S4 | **注释语言与代码语言系统性错配** | 整文件中文注释 + 纯英文标识符，两者规范度都异常高，且**同目录既有文件不是这个组合** |
| S5 | **过度文档化** | 每个函数都有五段式 docstring + 参数表 + 返回值 + 使用示例，覆盖率接近 100%，且**同目录基线明显更低** |

**五条强信号里，S3/S4/S5 属 T1 层，计 12 分的前提是“已内建基线对比”**：命中的不是“风格本身”，而是“与同目录既有文件的失配”。**没有可用人类基线时，这三条一律降为 4 分**（按中信号计），否则会把严格规范的团队判成 AI。

**S2 依赖基线，无基线时不可评**：它的判据本身就是“与同目录既有文件失配”，没有可比对象就不成立。这种情况要在报告里写“**未评估**”，**不能当成“没命中”**——否则一个整项目 AI 生成、没有人类基线的仓库，会因为 S2 天然无法成立而被系统性低估。

**S1 的三条排除条款**：

- 项目本身即 LLM 应用时，代码里出现供应商/模型标识符（`gpt-4o`、`claude-3-5-sonnet`、`OPENAI_API_KEY`）属业务常量，**不算 S1**。S1 只认“生成器对自身的自述或自署名”。
- **`TODO` 本身不作为判据。** 人类随手写 TODO 极常见，带不带负责人、日期都不构成 AI 痕迹。S1 只认“函数体确实为空、文件却被当作完成品”这种组合，而不是“有一行 TODO 注释”。
- **文档示例里的占位符不算残留。** 若该行位于 docstring 的 `Examples:` 段，或行首是 `>>>` / `...` 提示符，那是在教用户怎么调用（`>>> # Your code here`），不是生成器留下的。**实测 ultralytics 有 3 处 `# Your code here` 全部属于这一类**——不排除就会凭 S1 一条把成熟开源项目判成“高度疑似”。

过滤示例占位符的写法：

```bash
grep -rniE "your code here|<placeholder>|此处填写" <target> --include='*.py' \
  | grep -vE ':[0-9]+: *(...|>>>)'      # 去掉 docstring 交互示例里的占位符
```

### 中信号（各 4 分，共 32）

| 编号 | 痕迹 | 判据 |
|---|---|---|
| M1 | 命名长度方差异常低 | 同作用域内标识符长度标准差显著小于仓库基线 |
| M2 | 注释密度恒定 | 每函数注释率的离散度极低（人类是忽高忽低） |
| M3 | 防御密度均匀 | 每函数必 try/catch、每参数必校验，与真实风险不匹配 |
| M4 | 模块结构四件套对称 | 每个业务目录都有 `index` + `service` + `types` + `utils`，且内容都很薄 |
| M5 | 复制粘贴块集中 | 新增文件的重复块密度显著高于仓库基线 |
| M6 | 配置项无人使用 | `options.xxx` 定义了但全仓库无任何调用方传值 |
| M7 | 两套等价接口并存 | 同步/异步、callback/Promise 双份实现，无说明 |
| M8 | 测试形态单一 | 断言几乎全是 `toHaveBeenCalled` 类，或断言只有 `toBeDefined` |

### 弱信号（各 2 分，共 8）

| 编号 | 痕迹 | 判据 |
|---|---|---|
| W1 | 语法糖过量 | 一律推导式、`useMemo`/`useCallback` 无差别包裹、可推断类型也标注 |
| W2 | 排版与导入排序过度规整 | import 分组、空行间距、段落长度明显比同目录文件更“标准” |
| W3 | 文件头 README 腔 | 开篇大段“本模块负责……采用了……设计” |
| W4 | 礼貌式错误文案 | “抱歉，操作未能完成，请检查您的输入”且无机器可读错误码 |

**满分 100** = 5 条强信号（各 12）+ 8 条中信号（各 4）+ 4 条弱信号（各 2），共 17 条全部命中（现实中不会出现，它只是量程上限）。若按上文降级规则把 S3/S4/S5 计为中信号，量程上限降为 76 分；判定区间照旧按绝对分适用，不随量程缩放。

### 轴 B：纪律分（三条判据，独立于 100 分制）

测的不是“多出来了什么”，而是“**本该有的东西没有**”。逐文件计算，工具：`python scripts/trace_probe.py <target> --baseline <人工语料目录>`。

> **轴 B 目前只支持 Python。** `trace_probe.py` 用 `ast` + `tokenize` 解析，只认 `.py`。JS/TS、Java、Go 等项目**轴 B 整体不适用**：报告写明“纪律层不适用于该语言”，判定只走轴 A，不得用轴 A 的 0 分反推“未检出”。

| 编号 | 判据 | 阈值 | 人类为什么不这样 |
|---|---|---|---|
| **D** | **文档风格偏离** | 文档覆盖 ≥ 0.70 **且** 注释率 ≤ 0.20 **且** 私有/公共文档比 ≥ 0.85（函数数 ≥ 5） | 人只给对外接口写文档，内部实现与一行 setter 直接略过 |
| **S** | **注释组织偏离** | 分区注释 `# ==== 标题 ====` ≥ 3 条/千行 | 人会分节，但不会给几乎每一块代码都起标题 |
| **T** | **注释位置偏离**（辅助，不参与判定） | 行尾注释占比 ≤ 30%（注释 ≥ 20 条） | **这条不可靠**：CPython 标准库本身就有 71% 的文件满足，不能当证据 |

**D 与 S 必须同时成立**，轴 B 才算成立。三条判定条件：

1. D 的命中文件占比 ≥ 30%
2. S 的命中文件占比 ≥ 30%
3. 命中（D∧S）的文件 ≥ 4 个

**为什么是合取，而不是“三条中命中两条”**——这是被一个真实的假阳性教出来的：

早先把“文档覆盖”与“可见性无落差”分成两条，实测两者高度共线（都是“docstring 全覆盖”的两种说法）。用“≥2/3”时，ultralytics（116 个计分文件，强制全项目 docstring，含私有方法）有 48 个文件同时命中那两条，**整项目命中率 44%，倍数 10.5×，会被判成“高度疑似”**——但它是一个规范严格的人工开源项目。改成 D∧S 后，同一项目降到 **0/116**。

结论：**单独一条判据只反映项目风格；两条性质不同的判据同时偏离，才指向生成过程。**

**残留物不计分**（注释掉的代码 / TODO / 未用 import）：人工语料里 62.6% 的文件本身就“零残留”，按体量过滤后 600 行以上仍有 36.2%，区分度太弱。它只在**分组之后**（把某几天生成的那批单独拎出来）才有解释力，作辅助读数写进报告。

**绝对值没有意义，必须除以人工基线。** 判读固定为倍数：

| 倍数（目标命中率 ÷ 基线命中率） | 含义 |
|---|---|
| < 3× | 不可解释，按未检出处理 |
| 3×–10× | 中信号，需其它证据配合 |
| **≥ 10×** | 可作强证据，判定至少“混合” |

**没跑基线就不要报纪律分**，只把它当作中信号。实测参照（同一探针）：

| 语料 | 计分文件 | D | S | 命中 D∧S | 命中率 |
|---|---|---|---|---|---|
| CPython 3.13 标准库 | 361 | 3% | 5% | 1 | **0.3%** |
| ultralytics（OSS，强制 docstring） | 116 | 41% | 3% | 0 | 0% |
| Swin-Transformer（OSS） | 20 | 0% | 90% | 0 | 0% |
| MISSFormer（OSS） | 50 | 0% | 38% | 0 | 0% |
| CDSS-PIC（已知 AI 生成） | 15 | 40% | 93% | 5 | 33.3% |

注意 ultralytics 与 Swin-Transformer 这两行：**各自都有一条判据很高**（41% / 90%），但没有一条项目同时过两条线。这正是合取规则要挡的情形。

两轴组合的读法：

| 轴 A（表层） | 轴 B（纪律） | 解释 |
|---|---|---|
| 高 | 低 | **AI 速成**：一次生成、未经过人工打磨 |
| 低 | 高 | **迭代式生成**：多轮 agent + 人类把关，文体被压平、纪律还在 |
| 高 | 高 | 迭代后未清理，或人类严格照规范重写 |
| 低 | 低 | 未检出（不等于人工） |

### 判定区间

**强信号条数是主判据，总分只在相邻档之间加权（阈值见下表），不单独决定档位。** 两者不互相“抢结论”，避免出现“分数够了但一条强信号都没有”也判为混合的情况。

**自上而下取第一条满足的条件即止。** 前置限制：**若命中的强信号全部为 S3/S4/S5（同属 T1 层），最高只能判到“混合”——跳过“≥3 条强信号”那一条，直接从“其余 ≥2 条强信号”往下取。**

**第二道前置限制：代码被“去 AI 味”改写过时，T1/T2 证据作废，改由 T3 单独决定。** 判据不是“有没有去味工具”，而是“**有没有写回过代码**”：必须看到其一——改前/改后成对的代码文件、脚本中存在写入动作（`open(..., 'w')`、`write`）且作用对象为 `.py`、或“重构前/重构后”的代码快照。**只扫描并打印的审计脚本不构成证据**（例如只输出“过短/过长注释”清单的检查器），这种情形 T1/T2 照常有效。一旦确认改写过，T1/T2 的“未命中”一律失效；若无 T3 证据兜底，判定为“证据不足”，**不得判“未检出”**。**同理轴 B 偏低也不能当反证**——去味改写本身就是打散纪律，纪律层归零恰恰是改写的预期结果。

**第三道前置限制：AI 代理工作区是证据，不是加分项。** 若仓库内存在代理的会话/记忆记录（`.workbuddy/memory`、`.claude/projects`、`.cursor/` 等），且代码文件的修改时间落在这些会话期内，视为“**AI 参与已确认**”：判定**下限定为“混合”**，并写明“参与范围无法从文本确定”。只有当能证明该代理只作用于文档（如仅改写 `.md` / `.docx`）时才可豁免。此时同样禁止判“未检出”。

| 条件 | 结论 |
|---|---|
| 命中 **S1**（且已过排除条款） | **高度疑似**。这是直接证据，不需累加 |
| **轴 A**：≥3 条强信号（其中至少 1 条为 **S1 或 S2**），或（2 条强信号且总分 **≥64**） | **高度疑似**（速成型），人工痕迹极少 |
| **轴 B**：成立（D、S 均 ≥30% 且命中 ≥4 文件）**且**倍数 **≥10×** | **高度疑似（迭代型）**：agent 逐模块生成 + 人类把关。此时轴 A 可能全空，**这是正常形态，不是矛盾** |
| **轴 A**：其余 **≥2 条强信号**的情形（2 条且总分 <64，或强信号全部属 T1 层），或（1 条强信号且总分 **≥30**） | **混合**：AI 起草 + 人工编辑（最常见，也最难判） |
| **轴 B**：倍数 **3×–10×**（且轴 B 成立），或倍数 ≥10× 但轴 B 不成立 | **混合** |
| **轴 A**：1 条强信号且总分 **<30**；或 **0 条强信号**且总分 **≥15** | **证据不足**：只报“疑似”，不给结论，写清还缺什么 |
| **轴 A 与轴 B 都低**（轴 A 无强信号且 ≤14 分；轴 B <3×） | **未检出 AI 痕迹**。只说明“按本信号集没找到”，**不等于“人工书写”**（见硬纪律 7） |

**轴 B 未测时不能直接落最后一档。** 先跑探针；确实拿不到人工语料，就写“纪律层未校准，结论为未检出”，并且**不得**写成“人工书写”。

**为什么“迭代型”可以判到高度疑似，而全 T1 必须封顶在混合**：T1 测的是文体，文体被多轮改写压平后既可能“全空”也可能“残留零星”，其本身不携带生成过程的信息，而且判据依赖基线、是“严格规范团队”最主要的假阳性来源——这与 `references/traits-catalog.md` 末尾“仅 T1 命中不足以定性”是同一条约束。T4 测的是**跨文件的纪律一致性 ÷ 人工基线倍数**，依赖的是“人必然漂移、agent 不会”这一结构性差异，并且必须过校准这一关。前者是风格判断，后者是分布判断。

**64 这个阈值不是随手定的**：2 条强信号最多 24 分，中/弱信号全中再加 40 分，该配置的理论上限正好是 **64**。够到 64 意味着“除了第 3 条强信号，能拿的证据已经拿满”，判高度疑似才有实质依据。60 与 64 之间只差一条弱信号，实际区分度为零——所以直接取上限做线，比取中间值更干净。**这个论证只在完整量程（100 分）下成立**：S3/S4/S5 降级后满分降为 76，64 分只相当于约 84% 的证据，“拿满”的说法不再适用，该分支下 64 这条线的实质强度要按此打折理解。

**判定层级必须写明**：文件级判定用“该文件内”的强信号条数与得分；项目级判定用全项目累计值。两者结论可以不同，报告里要指明是哪一级。

**计分示例**：命中 S2、S3（24 分）+ M1、M2、M3（12 分）+ W1（2 分）= **38 分 / 100**，2 条强信号 → 混合。

**为什么用 100 分制**：17 条痕迹按 12/4/2 加权正好落在 0–100，档位阈值（64 / 30 / 15）与“1 条强信号 = 12 分”构成同一刻度；若 17 条等权各计 1 分，强信号与弱信号同权，3 条弱痕迹的份量就超过 1 条强痕迹，量纲失真。

**同时必须报“AI 参与面”**：命中文件数 / 扫描文件数，以及按目录的分布。项目往往是部分生成，单一总分不如这张分布图有用。

**“命中文件”的口径必须固定**：该文件命中 ≥1 条强信号，或 ≥2 条中/弱信号，即计为命中。不写死这条，参与面百分比不可复现。

> 这条口径**故意宽于判定门槛**：它回答的是“哪些文件值得看”，不是“这个文件是不是 AI 写的”。所以允许出现“参与面 62%、整体判定却是证据不足”的组合——那说明信号分散、每处都不够硬。报告里照实写，**不要为了让两个数字看起来自洽而去调参与面**。

**置信度只在判定落到“高度疑似 / 混合 / 未检出”时才写。** 判定为“证据不足”时不配置信度——给一个没有结论的结论标“中/低”，等于把不确定性又包装成了一个结论。

## 检测流程

### 第 1 步：定范围与基线

- 明确扫描对象：整个项目 / 指定目录 / 指定文件集。**默认排除** `node_modules`、`vendor`、`dist`、`build`、`out`、`target`、`coverage`、`.next`、`.venv`、`venv`、`env`、`__pycache__`、`.git`、`.mypy_cache`、`.pytest_cache`、`site-packages`、`migrations`、`testdata`，以及第三方拷贝代码、自动生成的锁文件（与 `scripts/trace_probe.py` 的 `EXCLUDE_DIRS`、`references/playbook.md` §1 保持一致）。
- **建两组基线，别混用**：
  - 项目内基线（轴 A 差分用）：取“确定由人写”的部分（核心模块、同目录的既有老文件）算注释率、命名长度、函数体量、防御密度。
  - 外部人工语料（轴 B 校准用）：一批公认人工维护的代码（标准库、成熟第三方库），只跑探针求命中率，用来当分母。**这一组在第 3 步之前就要准备好。**
- **没有基线就没有检测**，这是本技能与“凭感觉看”的分界线。若项目全部由 AI 生成、无项目内基线可比，轴 A 改用“内部一致性”判据（找同项目内的风格断层），轴 B 照常用外部语料校准。

### 第 2 步：先查 T3 元证据

顺序很重要——元证据最便宜且最硬：

```bash
# 1) 生成器残留（占位符、AI 自述）。必须带排除项，否则 node_modules 会淹没信号
grep -rniE "your code here|as an ai|作为一个 ?ai|insert .* here|generated by (gpt|claude|copilot)|<placeholder>|此处填写|待补充" <target> \
  --exclude-dir={node_modules,vendor,dist,build,out,target,__pycache__,.git,.venv,venv} \
  --exclude={*.min.js,*.bundle.js,*-lock.json,package-lock.json,yarn.lock,poetry.lock}

# 2) 空实现被当作完成品：def 之后紧跟 pass / NotImplementedError（-H 必须有：单文件输入时 grep 默认不打印文件名）
grep -rnH -A1 -E '^[[:space:]]*(async[[:space:]]+)?def ' <target> --include='*.py' \
  | grep -E -- '-[0-9]+-[[:space:]]*(pass|raise NotImplementedError)'

# 3) 工具与配置痕迹（只证明"用过 AI"，不证明"这段是 AI 写的"）
ls -a <target> | grep -iE "cursor|claude|aider|copilot|codex|windsurf|AGENTS|\.rules"
```

> JS/TS 的空实现可以用空块匹配补一条：`grep -rnE 'function[^{]*\{[[:space:]]*\}' <target> --include='*.ts'`，再确认该函数在调用侧被当成可用。

> **这些命令按 bash 语法书写。** `--exclude-dir={a,b,c}` 依赖 bash 的花括号展开，Windows 上须在 Git Bash / WSL 里执行；PowerShell 与 cmd 会把 `{a,b,c}` 原样传给 grep，排除项全部失效，node_modules 会淹没信号。另注意 `--exclude-dir` 里的 `target` 指 Maven / Gradle 的构建输出目录，**与占位符 `<target>` 无关**。

### 第 3 步：跑 T4 纪律探针（轴 B）

**这一步不能因为第 2 步没命中就跳过。** 迭代式生成的样本，元证据通常也干净。

```bash
P="<技能目录>/scripts/trace_probe.py"
python "$P" <target> --baseline "<人工语料目录>"
```

只读文件、`ast` + `tokenize` 静态解析，不 import、不执行被测代码，无需联网、无需装包。**基线不能省**：没有基线的纪律分没有解释力，只能当一条中信号。

拿到三个数：**D 命中率 / S 命中率 / 倍数**（脚本直接给，并会打印“轴 B 成立/不成立”）。**两条必须同时 ≥30%，且命中文件 ≥4 个**；任一条不过线就是项目风格，不是生成痕迹。倍数 <3× 直接当作没检出，不要拿绝对分说事。若项目没有文档串（D 恒不成立），**本层整体不适用**——报告写“纪律层不适用（无文档串）”，既不能记为未命中，也不能据此写“未检出”。

### 第 4 步：扫 T2 结构

文件体量分布、目录对称性、重复块、依赖清单形态。项目级信号在这一层最明显。

### 第 5 步：扫 T1 文体并与基线做差分

这一层**只能做差分判断**。绝对判据（“注释超过 30% 就是 AI”）在本领域是错的——严格规范的团队注释率同样高。要问的是：**这个文件与同目录其他文件比，哪里不一样？**

### 第 6 步：出结论

报分数 + 强/中/弱命中明细 + 轴 B 倍数 + AI 参与面分布 + 置信度，并明确写出“本结论是启发式排序，不是概率”，以及“不能判断的部分”。

### 第 7 步（可选）：去 AI 味改写

用户要求“让它不像 AI 写的”时进入改写流程，规则表见 `references/de-ai-rewrite.md`。

**硬约束：改写不得改变程序行为。** 改完必须跑测试；没有测试的先补测试再改，或只做零风险的注释/排版类改写。为了“不像 AI”而引入缺陷，是把可读性问题换成正确性问题——这比 AI 味严重得多。

## 硬纪律

1. **不做质量判断。** 不评 bug、不评可维护性、不评性能。看到疑似缺陷只留一行提示。
2. **不给伪概率。** 不写“83.7% 可能是 AI 生成”。只给区间结论 + 命中明细，让用户自己掂量。
3. **短片段不下结论。** 少于约 50 行、或单个函数的样本，归因结论一律标“证据不足”。代码的文体可变空间远小于自然语言，短样本基本不可检测。
4. **T1 不能单独定罪。** 严格 lint、统一模板、教程出身的作者都会产出高注释、齐命名的代码。S3/S4/S5 虽属 T1 层，但已内建“与同目录既有文件失配”这一基线条件（无基线时降为中信号，见评分量表）；即便如此，**命中全部落在 S3/S4/S5 上时最高只能判“混合”**，其余 T1 条目不得单独定性。
5. **必须报“不能判断什么”。** 经过大量人工重写的混合代码，归因基本不可靠——要直说，而不是硬给一个分数。若同时存在“去 AI 味”处理的证据，判定固定为“证据不足”（见判定区间的第二道前置限制），**不得判“未检出”**。
6. **改写不改行为。** 见上。
7. **“未检出”不等于“人工书写”。** 本技能只认痕迹、不认作者。0 分只说明“按当前信号集没找到”，不说明“是人写的”。报告里禁止把 0 分写成“这是人写的”“倾向人工”。**在给出“未检出”之前，必须先跑过轴 B 并报出基线倍数**——轴 A 归零只说明文体被压平了，不说明没有痕迹（见 `references/iterative-generation.md`）。

## 边界

- 归因检测阶段只做静态阅读与统计推理，**不运行被测项目的代码**：默认只用 grep / find / wc 一类文本与统计工具，外加 `scripts/trace_probe.py`（仅用 Python 标准库 `ast` + `tokenize` 解析源码，不 import、不执行被测代码，无需联网、无需装包）。`jscpd`、`pylint` 属可选外部工具（会下载包或依赖本机安装），**须先征得用户同意**，见 `references/playbook.md`。第 7 步改写阶段例外，必须跑测试。
- 轴 B 的纪律分**必须带基线**才成立。单次检测若拿不到人工语料当对照，纪律分只能作中信号，不得据此判“高度疑似”。
- 检测准确率受语言、框架、样本体量影响极大；**混合代码（AI 起草 + 人工大改）检出率最低**，这类情况应如实标注而非强行给分。
- 检测结论是**技术判断**，不具备任何法律或制度效力，不能作为处分、解雇、学术指控的依据。
