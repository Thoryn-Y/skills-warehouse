# 迭代式生成的纪律痕迹（T4 层）

适用场景：代码由 agent 分多轮、逐模块生成，期间有人类提供方向、取舍与修改意见；单轮产出量小，前后跨越数天到数周。

**这一层是为上一版技能的盲区补的。** 早先版本只认"过度生成"（注释过多、结构对称、满配防御），于是这类项目会拿到 0 分。0 分不代表没有痕迹，代表**测错了层**。

---

## 一、为什么文体层会失效，而纪律层不会

多轮生成会持续压平文体：

- 每轮只改几个文件，改哪个文件就按当次任务定量，全局的"均匀"自然碎掉；
- agent 读得到既有代码与架构文档，会跟随既有约定，不再"满配"；
- 人一旦说"少写注释""按现有风格"，S5/M2 的前提当场消失；
- 人被反复打磨过的文件，文体信号被稀释到基线以下。

所以**文体层的召回率随迭代轮数单调下降**。这是结构性的，不是阈值没调好。

但有一件事不会随迭代衰减：**注释与文档的书写习惯**。

人类在一个项目里持续数周，习惯会漂移——赶时间的那天少写文档，重构的那天多写注释，新学的写法只用在新文件里。agent 每轮开工都重新读同一份约定，把同一套规范**原样重放**到新文件上。它没有"那天太累了"。

由此得到本层要测的形状，它是否定式的——**不是"有什么"，而是"本该有的落差没有"**：

- 本该随函数重要性衰减的文档密度，不衰减（私有方法与公共方法一视同仁）；
- 本该参差的注释组织，高度统一（每块代码都顶着一个标题）；
- 本该两种写法的注释位置，只剩一种（只写块前整行注释，不写行尾）。

否定式证据的麻烦在于：它需要一个"本来该有多少"的参照。**这就是本层强制要求对照基线的原因**——见第四节。

## 二、三条判据（只有前两条参与判定）

全部由 `scripts/trace_probe.py` 用 `ast` + `tokenize` 静态计算（不 import、不执行被测代码）。阈值集中在脚本顶部 `TH` 常量里。

| 编号 | 判据 | 计算 | 人类为什么不这样 |
|---|---|---|---|
| **D** | **文档风格偏离** | 文档覆盖 ≥ 0.70 **且** 注释率 ≤ 0.20 **且** 私有/公共文档比 ≥ 0.85（函数数 ≥ 5、非空行 ≥ 100） | 人只给对外接口写文档，`_helper` 与一行 setter 直接略过 |
| **S** | **注释组织偏离** | 分区注释 `# ===== 标题 =====` ≥ 3 条/千行 | 人会分节，但不会给几乎每一块代码都起标题 |
| **T** | 注释位置偏离（**仅参考**） | 行尾注释占比 ≤ 30%（注释 ≥ 20 条） | **这条不可靠**：CPython 标准库本身就有 71% 的文件满足，不能当证据 |

### 为什么只有 D 与 S 算数

**T 是我先入为主写错的。** 我原以为"人写行尾注释、模型写块前注释"，但实测标准库的行尾注释占比是 56%、ultralytics 是 56%，而 AI 生成的样本是 18%——方向对，**可是标准库里也有 71% 的文件落在 ≤30% 这一侧**，说明它是风格分布而非生成痕迹。留着只会制造假阳性，降为参考。

**残留物（注释掉的代码 / TODO / 未用 import）同样不计分**：人工语料里 62.6% 的文件本身"零残留"，按体量过滤后 600 行以上仍有 36.2%。ps：ultralytics 有 139 处注释掉的代码、27 个 TODO——人工项目本来就长这样。

### 为什么必须 D 与 S 同时成立

这是被一个真实的假阳性教出来的，值得完整记下来：

初版把"文档覆盖偏高"与"私有/公共无落差"拆成两条独立判据（B1、B2），用"三条中命中两条"做门槛。**结果 ultralytics（116 个计分文件，全项目强制 docstring、含私有方法）有 48 个文件同时命中这两条，整项目命中率 44%，倍数 10.5×，会被判成"高度疑似"。** 而它只是一个规范严格的人工开源项目。

根因：**B1 与 B2 不是两条独立证据，是同一件事的两种说法**（都在测"docstring 全覆盖"）。拆开计分等于给同一个属性记两分。

现在合成一条 **D**，并改为合取：

> 轴 B 成立 = D 的命中占比 ≥ 30% **且** S 的命中占比 ≥ 30% **且** 命中（D∧S）的文件 ≥ 4 个。

改完后同一项目降到 **0/116**。

**逻辑**：单独一条判据只反映"这个项目的文档/注释风格"，那是团队规范；**两条性质不同的判据同时偏离，才指向"不是人写的"**。

## 三、两轴的用法

本层不并入原来的 100 分制，因为两者测的是**不同的东西**，混在一个分数里会互相抵消：

| | 轴 A：表层分（0–100，原量表） | 轴 B：纪律层（D/S 合取） |
|---|---|---|
| 测什么 | 过度生成 | 文档与注释习惯的双重偏离 |
| 高分的形态 | 速成代码（单次、无上下文、模板驱动） | 迭代式 agent 生成 |
| 人类高分可能 | 低（严格团队能到中段） | 低——需要两条同时偏离 |

| 轴 A | 轴 B | 常见解释 |
|---|---|---|
| 高 | 低 | **AI 速成**：一次生成、没经过人工打磨 |
| 低 | 高 | **迭代式生成**：多轮 agent + 人类把关。文体被压平，纪律还在 |
| 高 | 高 | 迭代生成后没有清理，或人类严格按规范重写 |
| 低 | 低 | 未检出（不等于人工） |

**不要因为轴 A 是 0 就停止检测。** 这正是本层存在的理由。

## 四、必须做对照校准

D、S 的绝对值没有意义。**同一个探针必须先在一批公认人工维护的代码上跑一遍**，得到基线，再解释目标项目的数字。

理由很实在：严格规范的人工库会命中单条判据。实测（同一探针、同一阈值）：

| 语料 | 计分文件 | D | S | 命中 D∧S | 命中率 |
|---|---|---|---|---|---|
| CPython 3.13 标准库 | 361 | 3% | 5% | **1** | **0.3%** |
| ultralytics（OSS，强制 docstring） | 116 | 41% | 3% | 0 | 0% |
| Swin-Transformer（OSS） | 20 | 0% | 90% | 0 | 0% |
| MISSFormer（OSS） | 50 | 0% | 38% | 0 | 0% |
| CDSS-PIC（已知 AI 生成） | 15 | 40% | 93% | 5 | 33.3% |

看后三行人工语料：**每一行都有一条判据很高**（ultralytics 的 D 41%、Swin 的 S 90%、MISSFormer 的 S 38%），但没有一条能同时过两条线。**这正是合取规则要挡的形状。**

判读标准（固定下来，不要临场调）：

| 倍数（目标命中率 ÷ 基线命中率） | 含义 |
|---|---|
| < 3× | 不可解释，按未检出处理 |
| 3×–10× | 中信号，需其他证据配合 |
| **≥ 10×** | 可作强证据，判定至少"混合" |

**没有跑基线就不要报纪律分。** 一个孤立的"33% 文件命中"和"0.3%"放在一起才有信息量，单独看只是数字。

### 校准命令

```bash
P="<技能目录>/scripts/trace_probe.py"

# 目标项目（目录或清单文件均可），基线一次跑完
python "$P" <target> --baseline "<人工语料目录>"

# 人工语料示例（按本机情况选）：
#   Python 标准库   $(python -c 'import sys;print(sys.base_prefix)')/Lib
#   某成熟第三方库  <site-packages>/<lib>
#   项目内老文件    清单文件（每行一个路径）

# 额外排除目录，可重复；匹配的是目标根之下的路径分量
--exclude 备份 --exclude 软著相关
```

## 五、两个标定样本

### 5.1 正样本：已知由 AI 生成的 Python 项目

27 个应用代码文件 / 7,021 非空行 / 跨 9 天多轮生成，人类提供方向与取舍；其中 21 个落在会话期内，另 6 个 mtime 早于会话期约半年、从研究代码库迁移而来。

| 指标 | 全项目（15 计分） | 会话期子集（14 计分） | 早期迁移（1 计分） | 人工基线 |
|---|---|---|---|---|
| D 命中 | 6/15 = 40% | 6/14 = 43% | 0/1 | 3% |
| S 命中 | **14/15 = 93%** | 13/14 = 93% | 1/1 | 5% |
| 命中 D∧S | **5/15 = 33.3%** | 5/14 = 36% | **0** | 0.3% |
| 分区注释密度 | 19.61/千行 | 22.22/千行 | 3.36/千行 | 1.23/千行 |
| 注释掉的代码 + TODO | 5 | **0** | 5 | 324 |

同一份代码，**轴 A 得 0 分、轴 B 倍数 120×**。这不是阈值问题，是入口问题。

项目内部还有一组天然对照：会话期生成的那 21 个文件，注释掉的代码与 TODO **合计 0**；而 6 个半年前迁移来的文件里有 5 处。同一仓库、同一目录结构、同一门语言，唯一变量是来源。

### 5.2 负样本：ultralytics（成熟 OSS）

178 个 `.py` / 116 个计分文件 / 50,026 非空行。

| 指标 | 实测 | 基线 | 判断 |
|---|---|---|---|
| D | 48/116 = 41% | 3% | 高——但这是项目强制 docstring 的结果 |
| S | 3/116 = 3% | 5% | **低于基线** |
| 命中 D∧S | **0/116** | 0.3% | 轴 B 不成立 |
| 注释掉的代码 / TODO | 139 / 27 | 109 / 215 | 正常人类量级 |
| 行尾注释占比 | 56% | 57% | 与人工惯例一致 |

**这个样本差点被误判。** 用初版"三条中命中两条"的规则，它命中率 44%、倍数 10.5×，会被写成"高度疑似（迭代型）"。合取规则把它降到 0。

它还暴露了另一处规则漏洞：项目里 3 处 `# Your code here`，全部出现在 docstring 的 `Examples:` 段（`>>> # Your code here`），是教用户调用的占位符。**按原 S1 规则会被当作"生成器残留"直接定案**。SKILL.md 的 S1 已补第三条排除条款。

## 六、本层仍然检不出的情形

如实列出，不要绕过：

1. **项目里没有文档串。** D 恒不成立，轴 B 无法成立（Swin-Transformer、MISSFormer 就是这种）。**这类项目本层根本不适用**——报告要写"纪律层不适用（无文档串）"，**不能写"未检出"**。
2. **文件数太少。** 命中文件 <4 个时不做项目级判定，只能逐文件看个案。
3. **人类重写过大部分内容。** 注释习惯会被人的漂移重新打散，D 与 S 同时失效。
4. **强制文档风格的团队。** 会拉高 D（ultralytics 41%）。这不会单独造成误判（还需要 S 同时过线），但会压缩 D 的区分力——遇到这类项目要特别看 S。
5. **注释极少的项目。** 注释率本来就低时 D 的"注释 ≤0.20"那一项恒成立，判据退化为"只看 docstring 覆盖"，需要在报告里说明。
6. **只判断"哪几行是 AI 写的"。** 本层给的是**项目级/文件级**参与判断，做不到行级归属。
7. **非 Python 项目。** 探针基于 `ast` + `tokenize`，只解析 `.py`。JS/TS、Java、Go 等项目本层整体不适用，判定只能走轴 A，且**不得用轴 A 的 0 分反推"未检出"**。

**使用纪律**：轴 B 成立、轴 A 为 0 时，报告要写清"文体层被压平，判定依据来自纪律层"，并列出 D、S 两条的命中率与基线倍数，让读者能自己复核。
