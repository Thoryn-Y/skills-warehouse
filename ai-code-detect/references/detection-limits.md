# 检测能力的真实边界与证据分级

**这份文件的作用**：当别人问“你凭什么说这是 AI 写的”，或者你要在报告里写一个结论时，用它来界定自己能说多硬的话。

---

## 一、检测准确率的真实上限（最重要的一节）

### 1.1 为什么代码比文章更难检测

自然语言的 AI 检测有统计基础：词汇分布、句长方差、罕见词偏好。**代码没有这个空间**：

- 多数操作只有一到两种规范写法（循环、条件、错误处理）；
- 语言与框架约定强制结构；
- lint 与 formatter 抹平风格差异；
- 两个工程师写同一个排序算法，产出几乎一致。

**结论**：代码的文体可变空间小 → 判别信息少 → 检测更难。这不是工具不够好，是任务本身信息量不足。

### 1.2 各类样本的可检测性

| 样本类型 | 可检测性 | 说明 |
|---|---|---|
| 整项目、未编辑、单一模型生成 | **高** | 结构对称 + 风格统一 + 元证据成片出现，多重信号叠加 |
| 单文件 300 行以上、未编辑 | 中高 | 三均匀（注释/防御/命名）通常成立 |
| 单文件 50～300 行 | 中 | 需要与项目基线对比才可靠 |
| 单个函数（< 50 行） | **接近零** | 不存在可用统计量 |
| 代码片段（十几行） | **零** | 无论用什么方法，结论都不成立 |
| AI 起草 + 人工大改 | **低，且是最常见的真实情况** | 信号被人工编辑打散，又不完全消失 |
| 人类写 + AI 润色 | 低 | 主体仍是人 |

**必须遵守的表达**：对“单函数/片段”不下结论；对“混合代码”明确标注“归因不可靠”。

### 1.3 公开工具的准确率声明

商业与学术检测工具（Originality.ai、GPTZero 等厂商推出的代码检测能力，以及 DetectCodeGPT 一类研究原型；产品名与功能范围以各家当前文档为准）在**未编辑的长样本**上可用，在**人工编辑后准确率骤降**；就各家公开的声明看，**没有一个在含人工编辑样本的评测上宣称超过约 80%**（**级别 C**：无独立复现；凡厂商自报数据，按引用纪律第 2 条标注“厂商数据”）。

这些工具的定位应当是**分诊**——把可疑文件挑出来给人看，不是给结论。把它们当作“检测结论”会同时产生两类错误：

- **假阳性**：严格规范的团队、教程出身的作者被误判；
- **假阴性**：AI 生成后经过一轮人工改名的代码被判为人写。

## 二、横向证据：文体特征确实在规模化出现

Trend Micro 对 19,000 个 MCP Server 仓库、**566,845 个文件**做确定性扫描，把文体特征作为 AI 参与判据：

| 指标 | 结果 |
|---|---|
| 单文件防御式代码块峰值 | 14,764 处／文件 |
| 含 >10 个 try-catch 的文件 | 6,109 个文件 / 1,586 仓库（**占仓库总数 8.3%**，不是文件占比） |
| 含 >5 个 try-catch 的仓库 | 约 19% |
| 含 emoji 的源码文件 | 19.3%（剔除 .md） |
| 含装饰性边框的仓库 | 23.6% |
| 含未使用 import 的仓库 | **50.3%** |
| 作者据此估算的 AI 使用比例 | 至少 20% |

- **级别：B**（探测性研究，特征集与阈值由作者自定，无外部验证）
- 来源：Trend Micro, *Hunt Them All*, 2025
- **正确用法**：证明“这些特征在真实仓库里足够普遍，值得作为检测项”；**不能反向**用于给单个仓库定罪。

## 三、结构痕迹的规模化背景

GitClear 分析 2.11 亿行变更代码（2020-01 至 2024-12，含 Google／Microsoft／Meta 等仓库与开源项目）：

| 指标 | 2020 | 2021 | 2022 | 2023 | 2024 |
|---|---|---|---|---|---|
| 移动行占比（重构信号） | 24.1% | 24.8% | 20.5% | 15.8% | **9.3%** |
| 复制粘贴行占比 | 8.3% | 8.4% | 9.4% | 10.6% | **12.3%** |

关键事实：**2024 年是有记录以来第一次“复制粘贴行 > 移动行”**；含 5 行以上重复块的频率在 2024 年增长约 8 倍（原文：*an 8-fold increase in the frequency of code blocks with 5+ duplicated lines during 2024*）。

- **同一份报告里有两个 2024 移动行值，两个都是真的**：PDF 中 "Percent of Changed Lines Moved for Refactoring, by Year" 图给出 **9.3%**（本表采用），而同一份 PDF 的七类操作表 "2024 Actual" 行给出 **9.5%**。二手报道普遍转引后者，才出现 9.3 / 9.5 并存。同理，2021 年在两张表里分别是 24.7% 与 24.8%。引用时注明取自哪张表即可，不必二选一。
- **8 倍 ≠ 4 倍**：8 倍指“含 5 行以上重复块的频率”，4 倍是该报告对外标题里的 *4x more code cloning*（代码克隆总量口径）。两个不同指标，别混用。
- **同一列不可跨表拼用**：既然两张表取值不同（2021：24.7 / 24.8，2024：9.3 / 9.5），引用时须整列取自同一张表。逐格挑对自己论点有利的版本，等于造假。
- **级别：A**，但方法学有争议（其算法在变量改名时会低估 “moved”，可能夸大恶化幅度）。
- **对本技能的意义**：为 T2-3“复用关系缺失”和 M5“复制粘贴集中”提供了基线量级——重复块**密度显著高于仓库自身历史水平**才构成证据，绝对值（比如“有 3 处重复”）没有意义。
- 注意：这份数据的原始议题是“代码质量下降”，**本技能只借用其中的重复率指标，不采纳其质量结论**。

## 四、模型与工具方言（用于缩小来源猜测范围）

不同生成器的默认习惯不同。这**不能**证明代码是 AI 写的，但能在已判定为 AI 生成之后，帮助判断“大概是哪一类工具”，或者反过来解释“为什么这个项目的风格是这样”。

| 来源 | 较强特征 | 弱项 |
|---|---|---|
| Claude 系（终端/代码模式） | 复述式注释、完整 JSDoc、TODO 注释、不必要的 helper | 说明性文字过多 |
| GPT 系 | 泛化命名、防御式守卫、吞异常的 try/catch | 输出冗长、跨文件重复工作 |
| Copilot（编辑器补全） | 三段式重复模式、泛化命名 | 单行补全通常干净，多行则不然 |
| Cursor（composer） | `useCallback` / `useMemo` 到处用、`import * as React` | 应用改动时会重排 import |
| Aider | 输出较干净，继承底层模型默认 | 偶尔残留冲突标记 |
| Tabnine | 类型注解全覆盖、偶发过时模式 | 较少编造库 |

**级别：C**（经验观察，来自公开的工程笔记与实践总结，无控制实验）。

**用法限制**：同一模型在不同工具、不同提示下产出不同。**不要**用它做“作者归属”断言，只能作为风格解释的辅助。

## 五、证据分级与引用纪律

| 级别 | 定义 | 可否作为结论依据 |
|---|---|---|
| **A** | 大样本仓库遥测（百万行级）、同行评审论文、预注册实验 | 可以，须注明方法学争议 |
| **B** | 厂商报告、行业调查、企业披露 | 趋势证据，须注明利益相关性 |
| **C** | 工程博客、二手转述、经验观察 | 只能提示“值得查” |

**引用纪律**：

1. 每个数字后跟级别标记。
2. 厂商（卖扫描工具/检测服务）的数据标“厂商数据”。
3. 不合并异构数据。仓库遥测与开发者调查测的是不同东西，平均出来的数描述不了任何事。
4. 本领域广泛流传但无法追溯原始方法学的说法，写成“有报告称……（需核对原文）”，或者只描述现象不给数字——“注释密度在整个文件里几乎恒定”这个现象本身可独立验证，不必依赖某个百分比。

## 六、结论的效力边界

1. **技术判断，无制度效力。** 检测结论不能作为处分、解雇、学术指控、奖项评审的依据。
2. **不给概率。** “高度疑似（速成型 / 迭代型）/ 混合 / 未检出”三档足够。任何精确到小数点的“AI 生成概率”都是伪科学。
3. **必须留痕。** 报告里要写清用了哪些命令、看了哪些文件、基线取的是哪部分代码——让别人能复现你的判断过程，比结论本身更重要。

---

## 七、一个容易搞错的因果关系

**“代码能正常运行”完全不能作为“不是 AI 写的”的证据。**

AI 生成的代码在语法层面几乎总是正确的：能编译、能运行、能通过 lint。因此：

- 拿“跑通了”来反证“是人写的”是无效推理；
- 拿“有明显 bug”来推断“是人写的”同样无效——AI 的功能缺陷率不低，只是错在语义而非语法。

检测只认**生成痕迹**（文体、结构、元证据），与代码是否正确、能否运行为正交维度。这一点在写报告结论时必须守住。

## 八、两个标定样本：一次修正、一次翻车

本技能的纪律层（T4）是被两次真实测试校准出来的。两次都推翻了我自己的结论，记在这里是为了让后来的人不必重走。

### 8.1 第一次：把迭代式生成判成"人工"（漏判）

某作者确认「纯 AI 生成」的 Python 项目（27 个文件、7,021 非空行、跨 9 天多轮生成），按本技能**只跑轴 A** 得 **0 分 / 0 条强信号**。我据此写过「信号集不覆盖该形态」「没有可靠的文本判据」。

**那两句是错的。** 错的不是数据，是入口：只跑轴 A，把「轴 A 归零」当成了「无痕迹」。

补上轴 B 后，同一份代码：

| | 全项目（15 计分） | 会话期子集（14） | 早期迁移（1） | 人工基线（361） |
|---|---|---|---|---|
| D 文档风格 | 40% | 43% | 0% | 3% |
| S 注释组织 | **93%** | 93% | 100% | 5% |
| 命中 D∧S | **5/15 = 33.3%** | 5/14 = 36% | **0** | 0.3% |
| 倍数 | **120×** | — | 0× | — |

轴 A 为什么全空，逐条都对得上：注释率 2.1%–16.3%、无注释函数 36.4%、返回注解仅 2/27 文件、`__main__` 守卫仅 1/27、装饰线散在 14/27 文件、无生成器残留。旧信号集测的是"过度生成"，而这个项目逐模块生成、读过架构文档、被要求克制。

**同一份代码，轴 A 得 0、轴 B 得 33.3%（120×）。** 迭代压平文体，压不平注释与文档的书写习惯。

### 8.2 第二次：把规范严格的开源项目判成 AI（误判）

为检验假阳性，拿 ultralytics（成熟开源项目，178 个 `.py` / 116 个计分文件 / 50,026 行）跑同一套。

**用当时的规则（三条判据取两条），它命中 44%、倍数 10.5×，会被判成"高度疑似（迭代型）"。** 这是误判。

根因是我自己把判据写坏了：当时把"文档覆盖偏高"与"私有/公共无落差"拆成两条，而**这两条其实是同一个属性的两种说法**（docstring 全覆盖）。ultralytics 全项目强制 docstring，48 个文件同时命中这两条，分就凑够了。

修正：两条合并为 **D**，并改为 **D 与 S 必须同时成立**。同一项目随即降到 **0/116**：

| | ultralytics | 人工基线 | 判断 |
|---|---|---|---|
| D 文档风格 | 48/116 = 41% | 3% | 高，但这是项目风格 |
| S 注释组织 | 3/116 = 3% | 5% | 低于基线 |
| 命中 D∧S | **0** | 0.3% | 轴 B 不成立 |
| 注释掉的代码 / TODO | 139 / 27 | 109 / 215 | 正常人类量级 |
| 行尾注释占比 | 56% | 57% | 与人工惯例一致 |

**同一次测试还暴露了 S1 的漏洞**：该项目有 3 处 `# Your code here`，全部在 docstring 的 `Examples:` 段里（`>>> # Your code here`），是教用户调用的占位符。按原规则会被当作"生成器残留"直接定案——**一条就够判高度疑似**。已在 SKILL.md 补第三条排除条款。

### 8.3 这两次修正的代价与教训

- 纪律层的召回率下降：CDSS-PIC 的命中文件从 10/15 降到 5/15（33.3%）。**这是为准确性付的价**——换来的是 ultralytics 从 44% 降到 0。
- 基线从"4.2%"重算为"0.3%"，倍数从 16× 变成 120×。**两个数字都别跨版本混用。**
- 判据之间的**独立性**比判据条数重要。两条高度共线的判据不构成"两条证据"。
- 单条判据只要够宽，任何规范严格的项目都能满足。**必须两条不同性质的同时偏离。**

### 8.4 这不代表它变成了「人工」

即使轴 B 成立，以下判断仍然**做不到**：

- **哪几行是 AI 写的**——只能到项目级/文件级，行级归属在没有生成日志时不可信；
- CDSS-PIC 的 15 个计分文件里仍有 10 个未命中 D∧S，**逐文件判会漏 2/3**；
- 人类若重写过大部分内容，书写习惯会被人的漂移重新打散，两层一起归零；
- 无文档串的项目（Swin-Transformer、MISSFormer）本层整体不适用。

### 8.5 使用纪律

1. 拿到轴 A = 0 时，**必须**继续跑轴 B 并报出 D、S 两条的命中率与倍数，不得直接下「未检出」。
2. **轴 B 必须 D 与 S 同时过线**（各 ≥30%、命中 ≥4 文件）。只过一条是项目风格。
3. 判定仍要写「本结论是启发式排序，不是概率」。
4. S1 命中要先看**是不是 docstring 示例**，别把 `>>> # Your code here` 当残留。
5. **不要为了「让它有反应」而下调阈值。** 正确做法是换信号族、做基线校准，而不是放宽标准——这两次修正走的都是前一条路。
