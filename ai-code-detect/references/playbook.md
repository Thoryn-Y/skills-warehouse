## 一、扫描前：范围与排除项

**默认排除**（否则噪声会淹没信号）：

```
node_modules/  vendor/  dist/  build/  out/  target/  coverage/  .next/
__pycache__/  .venv/  venv/  env/  site-packages/  .git/
.mypy_cache/  .pytest_cache/  migrations/  testdata/
*.min.js  *.bundle.js  *-lock.json  package-lock.json  yarn.lock  poetry.lock
*.generated.*  *.pb.go  *_pb2.py
```

排除的理由：这些要么是第三方拷贝，要么是工具生成的——**它们的“AI 味”来自生成器，不是来自写代码的人**，计入会把整项目判成 AI。

> 清单里的 `target/` 指 Maven / Gradle 的构建输出目录，与下文占位符 `<target>`（扫描对象）不是一回事，别把两者混读。

```bash
# 列出待扫描文件（示例：Python 项目）。清单落在【当前工作目录】的 .scan/，不要写被扫描目录内部的路径，也不要写 /tmp
mkdir -p .scan
find <target> -name '*.py' \
  -not -path '*/node_modules/*' -not -path '*/__pycache__/*' \
  -not -path '*/.venv/*' -not -path '*/venv/*' -not -path '*/env/*' \
  -not -path '*/site-packages/*' -not -path '*/migrations/*' -not -path '*/testdata/*' \
  -not -path '*/dist/*' -not -path '*/build/*' -not -path '*/target/*' -not -path '*/coverage/*' \
  -not -path '*/.mypy_cache/*' -not -path '*/.pytest_cache/*' \
  -not -name '*_pb2.py' \
  | sort | tee .scan/scan_list.txt | wc -l
```

> **本手册所有命令按 bash 语法书写。** `--exclude-dir={a,b,c}` 依赖 bash 花括号展开，Windows 须在 Git Bash / WSL 下执行；PowerShell 会把 `{a,b,c}` 原样传给 grep，排除项全部失效。

## 二、建立基线（这一步不能省）

没有基线，T1 的所有判断都退化成主观印象。

### 2.1 选基线样本

优先顺序：

1. **同目录的既有文件**（最有价值，因为它控制了框架与领域因素）
2. **核心模块**（被最多文件 import 的那个）
3. **命名/注释风格与当下约定不一致的老文件**（文件头带旧版本号、旧作者名、`# 2019` 之类年份标记的，通常是人写的存量代码）

> 基线完全来自“文件与文件之间的对照”，所以**只有一个文件的目录无法建立基线**，该目录下的 T1 判断一律降级或不判。

### 2.2 算四个基线量

| 量 | 计算方式 | 用途 |
|---|---|---|
| 注释率 | 注释行 / 非空行 | 判 M2 |
| 无注释函数占比 | 完全没有注释的函数 / 总函数数 | 最有效的单指标，经验值：人类通常 30%～60%，AI 接近 0%（无公开方法学来源，仅作差分参照，勿当阈值） |
| 标识符长度标准差 | 变量名长度分布的 σ | 判 M1 |
| 每百行 try-catch 数 | try 块数 / 行数 × 100 | 判 M3 |

```bash
# 粗略注释率（Python）。tab 分隔，路径含空格也不会错列
while IFS= read -r f; do
  total=$(grep -cvE '^[[:space:]]*$' "$f")
  cmt=$(grep -cE '^[[:space:]]*#' "$f")
  printf '%s\t%s\t%s\n' "$f" "$cmt" "$total"
done < .scan/scan_list.txt | awk -F'\t' '{printf "%s\t%.2f\n", $1, ($3>0 ? $2/$3 : 0)}' | sort -k2 -n

# 无注释函数占比（Python）：def 行之后 2 行内是否出现 docstring，输出真比值而非计数。
# 只在 scan_list 上统计，避免 .venv / site-packages 的第三方代码混进分母
total=$(tr '\n' '\0' < .scan/scan_list.txt | xargs -0 -r grep -E '^[[:space:]]*(async[[:space:]]+)?def ' | wc -l)
doc=$(tr '\n' '\0' < .scan/scan_list.txt | xargs -0 -r grep -A2 -E '^[[:space:]]*(async[[:space:]]+)?def ' | grep -c '"""')
awk -v t="$total" -v d="$doc" 'BEGIN{ if (d>t) d=t;
  if (t>0) printf "无注释函数占比 %.1f%%（%d/%d）\n", 100*(t-d)/t, t-d, t; else print "N/A" }'

# 标识符长度标准差 σ：同目录与全项目各跑一次，比 σ 而不是比绝对值
# v<0 的保护是防浮点舍入：方差理论上非负，但大 n 下可能算出极小负数，sqrt 会返回 nan
tr '\n' '\0' < .scan/scan_list.txt | xargs -0 -r grep -hoE '\b[a-zA-Z_][a-zA-Z0-9_]{1,40}\b' \
  | awk '{n++; s+=length($0); q+=length($0)^2} END{ if(n>1){ v=q/n-(s/n)^2; if(v<0) v=0;
    printf "σ=%.2f  均值=%.2f  n=%d\n", sqrt(v), s/n, n } else print "N/A" }'

# 每百行 try-catch 数（全项目汇总；同目录再把 scan_list 换成该目录的文件跑一次）
while IFS= read -r f; do
  printf '%s\t%s\n' "$(grep -cE 'try:|try \{|except |catch' "$f")" "$(grep -cvE '^[[:space:]]*$' "$f")"
done < .scan/scan_list.txt | awk -F'\t' '{t+=$1; l+=$2} END{ if(l>0) printf "每百行 try-catch %.1f（%d/%d）\n", t*100/l, t, l; else print "N/A" }'
```

> 这几个数都只求量级：`doc` 用“2 行内出现 docstring”近似，会漏掉长签名、宽 docstring 缩进等情形；σ 会混入关键字与库名；try-catch 计数会把字符串里出现的 `catch` 也算上。目的是**与基线对比**，不是精确统计。

### 2.3 纪律层基线（轴 B，必须带对照）

上面的量都是“文体”，会被多轮改写压平。纪律层（文档风格 D、注释组织 S）不会——但它的**绝对值没有意义**，必须除以人工语料的基线。

```bash
P="<技能目录>/scripts/trace_probe.py"

# 1) 目标项目 + 人工对照，一次跑完（脚本会直接打印“轴 B 成立/不成立”）
python "$P" .scan/scan_list.txt --baseline "<人工语料目录>"

# 2) 人工语料三选一
#    a. 本机 Python 标准库（最省事，公认人工维护）
BP=$(python -c 'import sys;print(sys.base_prefix)')
#    b. 成熟第三方库目录
#    c. 本项目内确定由人写的旧文件清单（最贴合，但往往不足 100 个文件）
```

先看**轴 B 是否成立**：D ≥30% **且** S ≥30% **且** 命中（D∧S）≥4 个文件。**任一条不过线就是项目风格，不是生成痕迹**——ultralytics 的 D 是 41%，S 只有 3%，按单条会误判。

成立之后才看倍数：

| 倍数 | 处理 |
|---|---|
| < 3× | 视为未检出，不写进强信号 |
| 3×–10× | 中信号 |
| ≥ 10× | 可判“高度疑似（迭代型）” |

**为什么不能省基线**：CPython 标准库自身也有 **0.3%** 的文件命中（361 个计分文件里 1 个）。没有基线的“33% 命中”既不说明有问题，也不说明没问题。

> 探针只用 `ast` + `tokenize` 读源码，不 import、不执行被测代码、不联网、不装包。若项目没有 docstring，D 恒不成立，此时**本层整体不适用**：报告写“纪律层不适用（无文档串）”，不能记为未命中，也不能据此写“未检出”。

## 三、逐层扫描命令集

### T3 元证据（先做，成本最低）

本层全部只看文件内容。

```bash
# 1) 生成器残留（带排除项，否则 node_modules 会淹没信号）
grep -rniE "your code here|as an ai|作为一个 ?ai|insert .* here|generated by (gpt|claude|copilot)|<placeholder>|此处填写|待补充" <target> \
  --exclude-dir={node_modules,vendor,dist,build,out,target,__pycache__,.git,.venv,venv} \
  --exclude={*.min.js,*.bundle.js,*-lock.json,package-lock.json,yarn.lock,poetry.lock}

# 2) 空实现被当作完成品：def 之后紧跟 pass / NotImplementedError
# -H 不能省：<target> 若是单个文件，grep 默认不打印文件名，第二段 -数字- 正则就永远匹配不到
grep -rnH -A1 -E '^[[:space:]]*(async[[:space:]]+)?def ' <target> --include='*.py' \
  | grep -E -- '-[0-9]+-[[:space:]]*(pass|raise NotImplementedError)'

# 3) 工具与配置痕迹（只证明"用过 AI"，不证明"这段是 AI 写的"）
ls -a <repo> | grep -iE "cursor|claude|aider|copilot|codex|windsurf|AGENTS|\.rules"
grep -rniE "cursorrules|copilot-instructions" <repo> --include="*.*" -l
```

### T2 结构

```bash
# 文件体量分布（看是否过于集中）。多条件必须加括号，否则一旦追加 -exec/-delete 只对最后一个条件生效。
# 必须套排除项，并滤掉 wc 每批输出的 total 行——否则 node_modules 与合计数会被当成"巨型文件"塞进分布
find <target> \( -name '*.py' -o -name '*.ts' -o -name '*.js' \) \
  -not -path '*/node_modules/*' -not -path '*/dist/*' -not -path '*/build/*' -not -path '*/__pycache__/*' -print0 \
  | xargs -0 -r wc -l 2>/dev/null | grep -v '[[:space:]]total$' | sort -n | tail -40

# 重复块（可选，两条都属"改动本机环境"的动作：npx 会下载包、pylint 可能未安装。
# 须先征得用户同意；装不上就跳过，改用 T2-3 的表格人工比对重复实现的函数名）
npx jscpd --min-lines 8 --reporters console <target>              # JS/TS
python -m pylint --disable=all --enable=duplicate-code <target>   # Python

# 依赖清单 vs 实际使用：只取 dependencies 段，列出声明了但全仓库 import/require 不到的包。
# 路径必须指向 <target>，不能取 cwd 下的 package.json——两者常常不是同一个项目。
# path.resolve 用来把相对路径变成可 require 的绝对路径（否则 "proj/package.json" 会被当成包名）
mkdir -p .scan
node -e 'const p=require(require("path").resolve(process.argv[1]));Object.keys(p.dependencies||{}).forEach(k=>console.log(k))' "<target>/package.json" > .scan/deps.txt
while IFS= read -r p; do
  esc=$(printf '%s' "$p" | sed 's/[.[\*^$()+?{}|]/\\&/g')   # 包名里的 . + 等按字面匹配
  n=$(grep -rE "(from|require\()['\"]$esc(/[^'\"]*)?['\"]" <target> \
        --include='*.ts' --include='*.tsx' --include='*.js' -l 2>/dev/null | wc -l)
  if [ "$n" -eq 0 ]; then echo "未使用: $p"; fi
done < .scan/deps.txt
# 注意：devDependencies 里类型包与构建工具本来就不被直接 import，故只取 dependencies

# 目录对称性（看每个业务目录是否都恰好 N 个文件）。用 uniq -c 直接数，不要加 -w3：
# -w3 只比较前 3 个字符，会把"100 个文件"与"1000 个文件"的两组目录并成一条
find <target> -mindepth 2 -maxdepth 2 -type d -exec sh -c 'ls -1 "$1" | wc -l' _ {} \; | sort -n | uniq -c
```

### T1 文体

```bash
# 装饰性符号
grep -rnE "^[[:space:]]*(#|//).*(=====|-----|════|╔|🚀|✅|🔧)" <target>

# 复述式注释（粗筛：注释里出现 return/递增/初始化 等词）
grep -rniE "^[[:space:]]*(#|//).*(returns?|递增|初始化|设置|获取|检查)" <target> | head -30

# 防御密度：每百行 try-catch 数（与 §2.2 同一口径）。按密度排序，绝对数会偏袒长文件

# 语法糖过量（前端）
grep -rc "useMemo\|useCallback" <target> --include="*.tsx" --include="*.jsx" | sort -t: -k2 -rn | head

# 泛名密度
grep -roE "\b(data|result|info|obj|item|handler|manager|processor|service)\b" <target> --include="*.py" --include="*.ts" | wc -l
```

## 五、项目级视图（这是最有用的产出）

单一总分对“整项目”几乎没用，因为真实项目总是部分生成。要出的是**分布**。

### 5.1 AI 参与面热力表

```
| 目录          | 文件数 | 命中数 | 密度 | 判断        |
|---------------|-------|-------|------|-------------|
| core/         | 10    | 1     | 10%  | 人工为主     |
| ui/dialogs/   | 6     | 5     | 83%  | 高度疑似 AI  |
| utils/        | 12    | 9     | 75%  | 高度疑似 AI  |
| tests/        | 8     | 8     | 100% | 全量生成     |
```

### 5.2 怎么读这张表

- **集中度高**（少数目录 80%+，其余 10% 以下）→ 典型的人机分工：人写核心，AI 写外围。
- **全面均匀**（每个目录都在 50% 左右）→ 要么整体 AI 生成后人工过了一遍，要么基线建错了（把 AI 代码当成了人类基线）。
- **核心目录也高** → 注意：核心模块若由 AI 生成且历经多次人工修改，T1 信号会被打散，实际参与度可能被**低估**。

### 5.3 置信度怎么定

**先有判定，再谈置信度。** 判定为“证据不足”时不写置信度——那是给不确定性再包一层结论。

| 情形 | 置信度 |
|---|---|
| 命中 S1，且基线可用 | 高 |
| ≥2 条强信号且含 S1 或 S2，基线可靠 | 高 |
| 轴 B 成立（D、S 均 ≥30%）且倍数 ≥10×，已跑基线 | 高——对“AI 参与”本身；参与范围仍不可判，须注明 |
| 轴 B 有命中但没跑基线，或只过一条判据 | 低（未校准或未成立，只能作中信号） |
| 判定由前置限制给出（代理工作区 / 去味改写） | 高——对“AI 参与”本身；同时必须注明“参与范围不可判” |
| 仅 1 条强信号，或强信号全为 S3/S4/S5 | 中 |
| 判定已成立，但无人类基线（改用“内部一致性”判据） | 低 |
| 0 条强信号且总分 ≤14（判“未检出”） | 低——“没找到痕迹”不等于“证明是人写的” |
| 判定为“证据不足”（例如只有“三均匀”这 12 分） | 不写置信度 |
| 样本 <50 行 / 单个函数 | 不给结论 |

## 六、常见误判与处理

| 误判 | 表现 | 处理 |
|---|---|---|
| **把脚手架当 AI 生成** | 目录高度对称、文件命名统一 | 查是否由 CLI 生成（`create-*`、`startapp`）；看是否有脚手架配置文件 |
| **把严格规范当 AI** | 注释齐全、命名统一、格式化整齐 | 必须有基线对比；看是否有 lint 配置、code review 规范文档 |
| **把开源拷贝当 AI** | 风格与项目其它文件明显不符 | 搜关键代码片段是否来自公开库；看 LICENSE/出处注释 |
| **把迁移/导入当 AI** | 整批文件风格与项目不符、命名体系突变 | 看是否有 `migrated from` / `imported from` 之类注释、README 说明，或旧版本号残留 |
| **把教程项目当 AI** | 教科书结构、注释密集 | 问用途；教学代码本来就这样 |
| **低估混合代码** | 判定为“人工”但实际 AI 起草 | 检查是否有风格断层（上半部分与下半部分不像同一人写的） |
| **把去 AI 味后的代码当人工** | 注释稀疏、找不到残留、得分接近 0 | 先找 `去AI味` / `humanize` / `_改前原件` / “重构前·后”快照，**并确认脚本真的写回过 `.py`**（只扫描打印的审计脚本不算）；是则判定固定“证据不足”，不得判“未检出” |
| **把迭代式生成当人工**（最常见的漏判） | 轴 A 全空：注释稀疏、无生成器残留、体量长尾、结构不对称 | **不要就此收工。** 跑轴 B：文档风格 D 与注释组织 S 是否**同时**偏离。这是多轮 agent 生成的**预期形态**，不是反证 |
| **把强制文档风格的项目当 AI**（实测过的坑） | 全项目每个函数都有 docstring，连私有方法和一行 setter 都写；D 命中 40%+ | **单看 D 必错。** ultralytics 就是这样：D=41%，但 S=3%，D∧S 命中 0/116。必须等 S 也过线 |
| **把格式统一的项目当 AI**（另一个坑） | 分区注释很密、整齐到像目录；S 命中 80%+ | 同理，Swin-Transformer S=90% 但 D=0%，一样不成立。**两条要同时** |
| **把顶级规范的人工库当 AI** | 文档覆盖高、注释少 | CPython 标准库 361 个计分文件里只有 1 个命中 D∧S（0.3%）。必须除以基线看倍数 |
| **把文档示例里的占位符当残留** | `>>> # Your code here` 出现在 docstring 的 Examples 段 | S1 排除条款第三条：示例占位符不算。ultralytics 有 3 处，不排除会直接定案 |
| **拿轴 A 的 0 分写“倾向人工”** | 报告结论与证据不符 | 禁止。轴 A 归零只说明文体被压平，先跑轴 B 再下“未检出” |

**通用对策**：任何单一结论在写进报告前，问一句“有没有非 AI 的解释？”——脚手架、迁移、开源拷贝、团队规范，这四类覆盖了绝大多数假阳性。

## 八、报告写作要点

1. 结论先行，且**三行说清**：判定 / 得分与参与面 / 置信度。
2. **每条证据必须可复现**：给出命令或文件行号，让别人能自己跑一遍。
3. 参与度与判定**分量列出**，不要合并成一个“AI 浓度”。
4. 明确写出“不能判断的部分”——一份标注了边界的报告，比一份看似完备的报告可信得多。
5. 不写“XX% 可能是 AI 生成”。三档结论 + 证据明细，足够专业。
6. 若用户目的是“去 AI 味”，报告末尾附改写清单，并提醒：**改完必须跑测试**。
