# 痕迹目录：T1／T2／T3 全量条目

每条给：**AI 典型 vs 人类典型**（对照表是本目录的核心用法）、**检测命令**、**误判风险**。

**检测的基本方法是差分**：不是问“这个文件有没有特征”，而是问“这个文件与同目录的其它文件，哪里不一样”。孤立判断几乎一定会冤枉规范严格的人类代码。

**本文件的命令按 bash 语法书写。** `--exclude-dir={a,b,c}` 依赖 bash 花括号展开，Windows 须在 Git Bash / WSL 下执行；PowerShell 会把 `{a,b,c}` 原样传给 grep，排除项全部失效。

## T3 元证据（可靠性最高，先查这一层）

### T3-1 生成器残留物

| AI 典型 | 人类典型 |
|---|---|
| 函数体是 `pass` 或 `raise NotImplementedError`，但文件被当作完成品 | 未完成功能有对应 issue 或注释追踪，文件不会被当作可用 |
| `<!-- 在此处填写 -->`、`[insert name]`、`<PLACEHOLDER>`、`# Your code here` | 模板文件会有，但同一项目里其它已有文件没有 |
| 注释里出现 `作为一个 AI 语言模型` / `As an AI` / `Generated by <model>` 类自述 | 不会出现 |

**`TODO` 本身不算痕迹。** 人类随手写 TODO 极常见，“带不带负责人/日期”也一样常见，二者都不构成 AI 证据。只有“**TODO 之后函数体为空、且文件已被当作完成品**”这个组合才算 S1 的第二类。

**不算 S1 的另一类**：项目本身是 LLM 应用时，代码中的 `gpt-4o`、`claude-3-5-sonnet`、`OPENAI_API_KEY` 等是业务常量，不是生成器残留。

```bash
grep -rniE "your code here|as an ai|作为一个 ?ai|insert .* here|generated by (gpt|claude|copilot)|<placeholder>|此处填写|待补充" <target> \
  --exclude-dir={node_modules,vendor,dist,build,out,target,__pycache__,.git,.venv,venv} \
  --exclude={*.min.js,*.bundle.js,*-lock.json,package-lock.json,yarn.lock,poetry.lock}

# 空实现被当作完成品（S1 第二类）：def 之后紧跟 pass / NotImplementedError
# -H 必须有：<target> 为单个文件时 grep 默认不带文件名，第二段正则匹配不到
grep -rnH -A1 -E '^[[:space:]]*(async[[:space:]]+)?def ' <target> --include='*.py' \
  | grep -E -- '-[0-9]+-[[:space:]]*(pass|raise NotImplementedError)'
```

**误判风险**：低——**但前提是先过上面两条排除条款**。否则“模型标识符”会命中所有 LLM 应用项目，而 S1 在量表里是免累加的直接证据，一次误判就把结论推到“高度疑似”。另需排除脚手架模板（`create-app` 留下的文件本来就有占位符），判据是“同项目其它文件是否也有”。

### T3-2 工具与配置痕迹

| AI 典型 | 人类典型 |
|---|---|
| `.gitignore` 里出现 `.cursor`、`.claude`、`.aider*`、`copilot-instructions.md`、`.github/copilot*` | 一般是团队显式引入的，会有讨论痕迹 |
| 仓库根出现 `AGENTS.md`、`.cursorrules`、`CLAUDE.md`、`.windsurfrules` | 同上 |
| 依赖里出现 `@anthropic-ai/*`、`openai` 而项目本身与 AI 无关 | 与业务相关的才会出现 |
| `package.json` / `requirements.txt` 里一行注释“由 XX 生成” | 无 |
| 仓库内有 `_去AI味*` / `humanize` 工作区、`_改前原件/` 与“改后”成对文件、或“重构前/重构后”基线快照 | 不会出现 |

```bash
ls -a <repo> | grep -iE "cursor|claude|aider|copilot|codex|windsurf|AGENTS|\.rules"
grep -rniE "cursorrules|copilot-instructions|generated by (gpt|claude|copilot)" <repo> --include="*.*" -l
```

**误判风险**：低，但要注意很多团队确实在用这些工具——**它证明"用过 AI"，不证明"这段代码是 AI 写的"**。作为加分项，不作定案依据。

**“去 AI 味”痕迹是例外，它比普通工具痕迹更关键**：普通工具痕迹只说明用过 AI；去味痕迹反过来说明**痕迹被清除过**，此时 T1/T2 的“未命中”全部失去效力，判定固定为“证据不足”（见 `SKILL.md` 判定区间的第二道前置限制）。

### T3-3 注释语言与代码语言系统性错配

## T2 结构指纹

### T2-1 文件体量分布异常

| AI 典型 | 人类典型 |
|---|---|
| 大量 300～800 行的"完整"文件 | 体量分布长尾：大量 50～150 行小文件 + 少量大文件 |
| 几乎没有 20～40 行的碎片文件 | 人类会随手建小模块 |
| 同目录文件行数接近（如 11 个文件都在 380～420 行） | 行数差异很大 |

```bash
# 必须套排除项并滤掉 wc 的 total 行：否则 node_modules 与每批的合计数会被当成"大文件"塞进分布
find <target> \( -name '*.py' -o -name '*.ts' -o -name '*.js' \) \
  -not -path '*/node_modules/*' -not -path '*/dist/*' -not -path '*/build/*' -not -path '*/__pycache__/*' -print0 \
  | xargs -0 -r wc -l 2>/dev/null | grep -v '[[:space:]]total$' | sort -n | tail -40
```

**判据**：体量分布**过于集中**。人类代码的行数分布是重尾的，AI 生成的是近似正态的。

### T2-2 模块结构过度对称

| AI 典型 | 人类典型 |
|---|---|
| 每个业务目录都是 `index` + `service` + `types` + `utils` 四件套 | 结构随实际需要生长，有的目录只有 2 个文件 |
| 目录树教科书化，层级整齐，每个目录都有 README | 局部混乱，有的目录没文档 |
| 空目录占位（`.gitkeep`）齐备 | 按需创建 |

**误判风险**：高。脚手架（NestJS CLI、Django startapp、Vue CLI）生成的目录本来就对称。判据是**业务逻辑目录**是否也如此整齐。

### T2-3 复用关系缺失

| AI 典型 | 人类典型 |
|---|---|
| 功能重复的 util 并存（`formatDate` / `toDateString` / `dateToString`） | 会复用，或至少有一个弃用注释 |
| 已封装的 HTTP 客户端不用，直接 `fetch`/`requests` | 沿用项目既有封装 |
| 同一段校验逻辑在 5 个文件里各写一遍 | 抽成共享模块 |

```bash
# 重复块检测（可选：npx 会下载包、pylint 可能未安装，属“改动本机环境”的动作，
# 须先征得用户同意；装不上就跳过，改用下表人工比对同名/近名的工具函数）
npx jscpd --min-lines 8 --reporters console <target>                         # JS/TS
python -m pylint --disable=all --enable=duplicate-code <target> 2>/dev/null  # Python
```

### T2-4 依赖引入形态

| AI 典型 | 人类典型 |
|---|---|
| 依赖清单里一次性堆入多个同类库 | 逐个引入，每次有理由 |
| 引入了与现有栈重复的库（已有 `dayjs` 又装 `date-fns`） | 复用现有 |
| 为一个小功能引入大库 | 手写几十行解决 |
| 清单里出现与项目功能无关的库 | 与业务相关才会出现 |

> 这一条只看**清单内容与代码实际用到的库是否对得上**：装了但全项目 import 不到，或功能重复的两个库并存，都算。

### T2-5 测试与实现同构

| AI 典型 | 人类典型 |
|---|---|
| 测试文件名与源码文件一一对应，数量整齐 | 覆盖不均：核心模块测得多，边缘模块没测 |
| 每个测试都是 mock + `toHaveBeenCalled` | 混合：单元、集成、端到端都有 |
| 断言只有 `toBeDefined` / `not.toThrow` | 断言具体值 |

```bash
grep -rc "toHaveBeenCalled\|assert_called\|verify(" <target> --include="*.test.*" --include="*_test.*"
grep -rc "toBeDefined\|assertIsNotNone\|assert result" <target> --include="*.test.*" --include="*_test.*"
```

## T1 文体指纹（只能做差分，不能单独定罪）

### T1-1 注释密度与复杂度脱钩

| AI 典型 | 人类典型 |
|---|---|
| `i += 1` 旁边写 `# 递增计数器` | 平凡代码不注释 |
| 每函数注释率几乎相同（离散度极低） | 复杂函数注释密集，简单函数一行没有 |
| docstring 覆盖率接近 100% | 只给公开 API 写 |

**关键指标**：不注释率（完全没有注释的函数占比）。经验值：人类代码通常 30%～60%，AI 生成接近 0%——**此区间无公开方法学来源，只能做差分参照，不可当绝对阈值**。

**对应评分量表 S5**（过度文档化）。S5 计 12 分的前提是“同目录基线的 docstring 覆盖率明显更低”；没有基线时按中信号 4 分计。

### T1-2 命名均匀

| AI 典型 | 人类典型 |
|---|---|
| 同作用域标识符长度标准差很小 | `get_user` 与 `computeAggregateMonthlyRevenue` 并存 |
| 泛名密集：`data`、`result`、`info`、`obj`、`handler`、`manager` | 业务语义明确的具体名 |
| 动词-名词模板整齐：`handleClick`/`handleSubmit`/`handleChange` 全套 | 命名约定不统一（不同时期写的） |

```bash
# 粗略统计：每文件标识符长度分布
grep -oE "\b[a-z_][a-zA-Z0-9_]{2,30}\b" <file> | awk '{print length($0)}' | sort -n | uniq -c
```

### T1-3 防御式编程均匀

| AI 典型 | 人类典型 |
|---|---|
| 每函数必 try/catch，包括不可能抛异常的三行工具函数 | 错误处理密度不均匀：痛过的地方细，没痛过的地方不写 |
| 每参数校验 2～3 次（跨层重复） | 校验一次，在边界做 |
| 每外部调用都 retry + 超时 + 降级 | 只在真会失败的地方加 |

**判据**：单文件 try-catch 计数 + **分布是否均匀**。均匀比数量更有辨识力。

### T1-4 语法糖过量

| AI 典型 | 人类典型 |
|---|---|
| 全部列表推导式，即使 for 循环更清楚 | 按可读性选择 |
| `useMemo`/`useCallback` 无差别包裹每个函数 | 只在真有性能问题处使用 |
| `const n: number = 1` 这类可推断标注 | 让类型推断工作 |
| `import * as React from 'react'` | `import { useState } from 'react'` |

### T1-5 排版节奏过匀

| AI 典型 | 人类典型 |
|---|---|
| 空行分布等距，函数之间恒为 2 空行 | 有的地方挤，有的地方松散 |
| 每个函数长度接近 | 长短悬殊 |
| 文件结尾恰好是某个整齐的边界 | 常常在任意位置结束 |

### T1-6 文件头说明腔

| AI 典型 | 人类典型 |
|---|---|
| 开篇大段："本模块负责用户认证流程，采用了 JWT 方案，主要包含以下功能：1. … 2. …" | 简短一句 module docstring，或什么都没有 |
| 把设计文档塞进源码 | 设计写在 README / 设计文档里 |

### T1-7 装饰性符号

| AI 典型 | 人类典型 |
|---|---|
| `# ==================== 分隔 ====================` | 偶尔有，但不密集 |
| `╔══════╗` box-drawing | 几乎不用 |
| 注释里的 emoji（`# 🚀 启动服务`） | 极少，且团队要么全用要么全不用 |

**关键**：判据是"**仅新文件有，老文件没有**"。若全项目都这样，那是团队风格。

**对应评分量表 S3**（12 分），上述“仅新文件有”就是它计入强信号的前置条件；无法确认时按中信号 4 分计。

### T1-8 礼貌式错误文案

| AI 典型 | 人类典型 |
|---|---|
| `"抱歉，操作未能完成，请检查您的输入后重试。"` | `"invalid input: field 'email' missing"` 或带错误码 |
| 错误信息是完整句子，面向终端用户 | 面向开发者，可 grep、可断言 |

### T1-9 注释语言与代码语言系统性错配

*（原编号 T3-3。它读的是“规范度与基线的差分”，不是生成过程留下的物证，所以归 T1 层，并按 T1 规则降级。）*

| AI 典型 | 人类典型 |
|---|---|
| 整文件中文注释 + 纯英文标识符，**两者都异常规范** | 混写时通常两头都不齐：中文注释随意，变量名也随意 |
| 注释语法完整、标点齐全、无口语、无缩写 | 有口语、有缩写、有拼写错误、偶尔中英夹杂 |
| 同一项目里，新文件注释语言与老文件不同 | 全项目注释语言一致（团队约定） |

判据不是“中文注释 = AI”，而是 **“规范度双高 + 与项目基线不一致”** 这个组合。中国开发者写中文注释极常见，**必须与基线对比，单文件不能判**。

**误判风险**：中高，与 T1 其余条目同级。

**对应评分量表 S4**（12 分）：计入强信号的前提是“同目录既有文件不是这个组合”；无基线时降为中信号 4 分。它与 S3/S5 同属 T1，**命中全部落在 S3/S4/S5 上时最高判“混合”**。

## T4 纪律痕迹（迭代式生成的主战场）

**这一层测的是「本该有的落差没有」，不是「多出来了什么」。** 完整方法论、阈值与校准纪律见 `references/iterative-generation.md`；此处只列条目与判读要点。

工具：`python scripts/trace_probe.py <target> --baseline <人工语料目录>`（`ast` + `tokenize` 静态解析，不 import、不执行）。

| 条目 | AI 典型 | 人类典型 | 是否计分 |
|---|---|---|---|
| **T4-1 文档风格偏离（D）** | 文档覆盖 0.8 而注释率 0.05；私有方法与公共方法文档覆盖率基本相等（比值 ≥0.85）；一行 setter 也写 docstring | 只给公共 API 写文档，`_helper` 与一行 setter 直接略过（基线比值 0.60） | **计分** |
| **T4-2 注释组织偏离（S）** | `# ===== 一、初始化 =====` 每千行 ≥3 条，整齐到像目录 | 会分节，但不会给几乎每一块都起标题 | **计分** |
| **T4-3 注释位置偏离（T）** | 只写块前整行注释，行尾注释占比 ≤30% | 边写边在行尾标注 | **仅参考**（stdlib 也有 71% 命中，不可靠） |
| **T4-4 残留物缺失** | 6,000 行里注释掉的代码 0 处、TODO 0 处——改完就清理 | 调试时注释掉几行忘了删；`# TODO: 以后再说`；删函数忘删 import | **辅助读数** |
| **T4-5 跨文件零漂移** | 跨数天、跨十几个文件，分区格式、文档句式完全一致 | 人的纪律随心情、deadline、新学的写法而漂移 | 由 D/S 的分布体现 |

**判定必须 D 与 S 同时成立**（各 ≥30% 且命中 ≥4 文件）。**单独一条只反映项目风格**：ultralytics 的 D 高达 41%（全项目强制 docstring），但 S 只有 3%，按单条会误判，按合取为 0。

**残留物为什么不计分**：人工语料里 62.6% 的文件本身"零残留"；ultralytics 有 139 处注释掉的代码、27 个 TODO。它只在**分组之后**（单独看某几天生成的那批）才有解释力，而分组需要 mtime 或来源信息，不属于纯文本判据。案例见 `iterative-generation.md` 5.1：会话期子集 0 处 vs 旧文件 5 处。

**判读必须除以人工基线。** 实测 361 个 CPython 标准库计分文件：D 3%、S 5%、D∧S 命中 **1/361 = 0.3%**。**只有倍数 ≥10× 才能作强证据**。

**误判风险**：中。已经被两条真实的假阳性校准过——ultralytics 的 D=41%（强制文档风格）、Swin-Transformer 的 S=90%（分区注释习惯），都只过单条。**没有基线就不要用这一层**。

**与轴 A 的关系**：T4 命中而 T1/T2 全空，是**迭代式生成的正常形态**，不是矛盾。这也正是旧版把这类样本判成 0 分的原因。

## 高辨识力组合（比单条更可靠）

单条痕迹容易误判，以下组合一旦出现，判定置信度显著上升：

| 组合 | 含义 |
|---|---|
| **S1 残留物 + 任意 2 条 T1** | 定性：生成时未清理 |
| **S2 与基线全面失配 + 存在人类基线代码** | 定性：这批文件不是同一支笔写的 |
| **T1 注释率均匀 + T1 防御均匀 + T1 命名均匀** | “三均匀”，AI 生成的核心指纹 |
| **T2-1 体量集中 + T2-2 结构对称 + S3 装饰符号** | 脚手架或整项目生成 |
| **3 条以上强信号同时成立** | 判“高度疑似”，且其中至少 1 条须为 S1 或 S2（元证据或结构层的失配）。三条全落在 S3/S4/S5 上时最高只到“混合” |
| **仅 T1 命中，无 T2/T3** | 不得判“高度疑似”。强信号全为 S3/S4/S5 时最高判“混合”；0 条强信号时只能报“证据不足”，不得判“混合” |
| **T4 轴 B 成立（D、S 均 ≥30% 且命中 ≥4）且倍数 ≥10×，而 T1/T2 全空** | 判“高度疑似（迭代型）”。**这不是弱证据**——文体被压平恰恰是多轮改写的预期结果，文档与注释习惯同时偏离才是人做不到的部分 |
| **T4 轴 B 成立 + 命中 T3-1（生成器残留）** | 双重确证：既留了物证，又有纪律分布 |

## 语言与框架的特殊判据

### Python
- 每个函数都有完整类型注解（含 `-> None`），而项目其它文件没有 → 强。
- `if __name__ == "__main__":` 出现在每个模块里。
- 大量 `try/except Exception as e: logger.error(e)` —— 无 `exc_info`、无类型区分。
- `dataclass` 用于只有 2 个字段的容器，且全项目统一。

### JavaScript / TypeScript
- `useMemo`/`useCallback` 覆盖率接近 100%。
- `interface` 与 `type` 混用，但每个文件内部高度统一（跨文件不统一）。
- 到处 `as any`、`as unknown as X`（说明生成时绕过了类型检查）。
- `console.log` 残留（AI 调试痕迹）。

### Java / C#
- 每个类都有完整 Javadoc / XML 注释，含 `@param` `@return` `@throws` 全覆盖。
- getter/setter 用 Lombok 但 `@Data` 与手写混用。
- 方法链过长且每步都 `Optional.ofNullable`。

### Go
- 每个函数都 `if err != nil { return fmt.Errorf("failed to xxx: %w", err) }` 且错误文案句式完全一致。
- 注释以函数名开头（正确但覆盖率 100% 异常）。

## 反向指标（帮助排除误判）

以下特征**指向人类书写**，可用于校准：

- 同一文件内风格断层（上半部分函数式、下半部分命令式）——人类在不同时间改的。
- 存在被注释掉的代码块——人类调试习惯。
- 拼写错误、缩写、口语化注释。
- 有 "为什么" 而无 "是什么" 的注释（`# 这里必须用 deepcopy，否则共享引用会互相污染`）。
- 函数长度差异极大（20 行与 300 行并存）。
- 存在明显的历史遗留：`# 暂时这样，等 v2 重构`。
- 测试覆盖不均：核心模块 90%，工具模块 0%。

这些出现得越多，“未检出”的可信度越高——但仍不等于“人工书写”，只说明该方向的反证偏多。
