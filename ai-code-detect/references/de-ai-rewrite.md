# 去 AI 味改写手册

## 前提：改写的目标不是伪装，是融入

一个项目的代码有“AI 味”，本质是**这批文件不像同一个工程团队写的**。所以去味的正当目标只有一个：

> 让新代码看起来像这个项目本来就有的代码。

这个目标下，改写规则与“提升可读性”高度重合——删掉复述式注释、去掉冗余防御、命名按语义来，本来就是好实践。**不要为了“不像 AI”而故意写得潦草**，那是把可读性换成伪装，得不偿失。

## 三条硬约束

1. **不改行为。** 改完必须跑测试。没有测试的模块，先补测试再改（或只做零风险的注释类改写）。
2. **不降低可读性。** 如果某条改写让代码更难懂，放弃它。AI 味重一点，比代码看不懂轻得多。
3. **保留真实的好实践。** 文档齐全、类型注解、错误处理本身不是 AI 味——**形式化的残留**才是。区分见下表。

| 该删（形式化痕迹） | 该留（实质好实践） |
|---|---|
| `i += 1  # 递增计数器` | `# 必须 deepcopy，否则两个实例共享同一列表` |
| 每个函数五段式 docstring | 公开 API 的 docstring |
| 每函数必 try/except | 真实会失败的外部调用处的 try/except |
| `# ========== 初始化 ==========` | 分区注释（如果项目其它文件也用） |
| `handleClick` / `handleSubmit` / `handleChange` 全套 | 真实的三个事件处理器 |
| `const n: number = 1` | `function parse(input: string): Result` |

## 改写规则（按行为风险从低到高排）

### R1 · 删复述式注释（风险：零｜收益：最高）

**判据**：注释把代码用自然语言说了一遍，不含任何代码里读不到的信息。

```diff
- # 遍历列表
- for item in items:
-     # 检查是否为空
-     if item is None:
-         # 跳过
-         continue
+ for item in items:
+     if item is None:
+         continue
```

**保留例外**：解释“为什么”的注释、指向外部原因的注释（issue 号、规范条款）、反直觉写法。

**操作**：先删一目了然的，再逐个判断剩下的。一个函数若删完注释后无法理解，说明那条注释该留。

### R2 · 打散注释密度（风险：零｜收益：高）

目标不是“少注释”，是**不均匀**。

- 复杂分支处补一句“为什么这么处理”。
- 三行的 getter 不写任何注释。
- 同一文件里，有的函数有注释，有的没有。

这正是人类代码的自然状态。**均匀本身就是最强的信号**，比注释多少更重要。

### R3 · 删装饰性符号（风险：零｜收益：中高）

```diff
- # ==================== 配置加载 ====================
+ # 配置加载
```
```diff
- # 🚀 启动服务
+ # 启动服务
```
```diff
- # ╔══════════════════════════╗
- # ║  用户认证模块             ║
- # ╚══════════════════════════╝
```

**例外**：如果项目里所有文件都用这个分隔符，那是团队风格，不要动单个文件——否则反而制造不一致。

### R4 · docstring 精简（风险：零｜收益：中高）

- 保留公开 API、会被他人调用的函数。
- 删除私有工具函数、显然函数（`get_name`、`is_empty`）的 docstring。
- 五段式（描述+参数+返回+异常+示例）压到一行，除非参数确实复杂。

```diff
- def add(a, b):
-     """
-     将两个数相加。
-
-     Args:
-         a (int): 第一个加数
-         b (int): 第二个加数
-
-     Returns:
-         int: 两数之和
-
-     Example:
-         >>> add(1, 2)
-         3
-     """
-     return a + b
+ def add(a, b):
+     return a + b
```

**注意**：如果项目有文档生成流程（Sphinx/pdoc），公开 API 的 docstring 不能删，否则会破坏文档构建。

### R5 · 命名去对称化（风险：低｜收益：高）

人类命名长度是随机的，AI 的是模板化的。

```diff
- const data = fetchData()
- const result = process(data)
- const info = format(result)
+ const rawOrders = fetchOrders()
+ const valid = rawOrders.filter(o => o.total > 0)
+ const summary = formatSummary(valid)
```

三条具体动作：

1. **泛名换业务名**：`data` → `rawOrders`，`result` → `valid`，`info` → `summary`。
2. **允许长度参差**：一个函数里既有 `id` 也有 `computeAggregateMonthlyRevenue` 是正常的。
3. **打破动词模板**：不必 `handleClick`/`handleSubmit`/`handleChange` 三件套，按实际语义命名（`onSaveDraft`、`submitOrder`）。

**操作建议**：用 IDE 的重命名重构，不要手动 sed——漏改调用点会直接破坏行为。

### R6 · 削减冗余防御（风险：中｜收益：高）

**先判断这个防御是否真的可能触发**，再决定删不删。收敛到一处，而不是全删：

```diff
- def format_price(value):
-     if value is None:
-         return ""
-     if not isinstance(value, (int, float)):
-         return ""
-     if value < 0:
-         return ""
-     try:
-         return f"¥{value:.2f}"
-     except Exception:
-         return ""
+ def format_price(value: float | None) -> str:
+     # 已核实唯一调用方 orders.py:118 只传 float 或 None，isinstance 与负数两处分支
+     # 是在确认契约之后才收敛掉的；将来新增调用方，就在这一处补回校验
+     if value is None:
+         return ""
+     return f"¥{value:.2f}"
```

**要点：注解不是运行时校验。** 写成 `value: float` 并不会拦住 `None`，把检查一并删掉等于让原来的 `""` 变成 `TypeError`——这就是改变行为。同理，`isinstance` 与 `value < 0` 这两个分支也不能顺手删：上游若会传字符串或负数，删掉就是改语义。**只有在确认调用方契约之后，才可以把它们收敛掉**。

**风险控制**：

- 删之前先确认调用方是否可能传 `None`。如果会，保留那一处检查（但只保留一处，不要每层都查）。
- 删 `try/except` 前确认里面真的不会抛。
- **永远不要删掉边界入口的唯一校验**（如 HTTP 入参、文件解析入口）——那不是 AI 味，那是必要的。

> 这一条最容易引入缺陷。改完必须跑测试，且要专门测一次空值/异常输入。

### R7 · 合并等价接口（风险：中高｜收益：中）

```diff
- def get_user(id): ...          # 同步版
- async def get_user_async(id): ...   # 异步版，无任何调用方
+ def get_user(id): ...
```

**先确认无人使用**（`grep -rn "get_user_async"`），再删。有调用方就先迁移调用方。

### R8 · 拆分无人使用的配置项（风险：中｜收益：中）

```diff
- def render(content, options=None):
-     options = options or {}
-     strict = options.get("strict", True)
-     pretty = options.get("pretty", False)
-     max_depth = options.get("max_depth", 10)
+ def render(content):
```

若全仓库没有任何调用方传 `options`，说明这些是生成时的“为了通用而通用”。删掉。

**例外**：这是对外发布的库，参数是公共 API 的一部分——那种情况要保留并补文档。

### R9 · 排版节奏打散（风险：零｜收益：中）

- 不必每个函数之间都空两行——按项目既有习惯。
- 允许函数长度悬殊。
- 不必在文件末尾凑一个"整齐"的结束。

**先查有没有格式化器**：项目若已启用 black / ruff-format / prettier / gofmt，甚至有自动格式化钩子，空行、缩进、import 排序都会被无条件改回去，R9 与 W2 属**无效改动**——做了也会被格式化器抹平，还可能与 CI 的 format check 冲突。这种情况直接跳过这两条，把精力放到 R1/R2/R10。

这一条单独做收益不大，但与其他条叠加后效果明显。

### R10 · 向仓库既有风格靠拢（风险：低｜收益：最高）

这是**最有效的一条**，应放在最后统一做：

| 维度 | 动作 |
|---|---|
| 注释语言 | 与同目录文件一致（老文件英文注释，新文件就别全中文） |
| 引号风格 | 单引号 / 双引号，跟项目走 |
| 缩进 | 空格数、tab，跟项目走 |
| import 组织 | 是否分组、是否绝对路径导入，跟项目走 |
| 错误处理 | 项目用返回值表示错误就别用异常，反之亦然 |
| 命名约定 | 驼峰 / 蛇形 / 前缀约定，跟项目走 |
| 文件组织 | 一个类一个文件 vs 多类一文件，跟项目走 |

**做法**：挑同目录下 2～3 个“确定是人写的”文件，把它们的风格特征列出来，然后逐项对齐。这比任何抽象规则都准。

## 改写后的验收

### 1. 行为不变（必做）

```bash
# 有测试就跑测试
pytest -q          # 或 npm test / go test ./...
```

没有测试的模块：至少手工跑一次主路径 + 一次边界（空输入、异常输入）。

### 2. 检测流程复测

用本技能的检测流程再跑一遍，**分数应当下降**，重点是：

- 注释率的标准差**上升**（从均匀变不均匀）→ 这是最直接的成功指标。
- S1（生成器残留）与 S3（装饰符号）应当清零；S2（与基线失配）会随 R10 的风格对齐一起消失。
- M2（注释密度恒定）、M3（防御均匀）应当消失。

如果分数没降，说明改的是表面（删了几条注释），没动到结构性的均匀性。

### 3. 人工可读性检查

找一段改过的代码，隔一天再读。如果读起来比改之前费劲，说明改过头了——**回退那一条**。

## 一个必须说清的权衡

“AI 味”和“可读性”有重叠区。注释多、文档全、防御足，在某种程度上确实是好习惯，只是 AI 把它做成了**没有取舍的满配**。

所以去味的正确做法不是“把好的都删掉”，而是**恢复取舍**：

- 该详的地方详（复杂逻辑、易错边界、反直觉实现）；
- 该简的地方简（三行 getter、显然的循环）。

人类代码的价值不在于“乱”，而在于**注意力有分配**。改写要复原的正是这种分配，而不是制造混乱。

---

## 适用与不适用

- **代码库自身的风格统一**、让新代码融入既有工程：这是本手册的正常用途。
- **已发布的公共库**：改动 API 形态（R6/R7/R8）需按语义化版本处理，不能当风格问题做。
